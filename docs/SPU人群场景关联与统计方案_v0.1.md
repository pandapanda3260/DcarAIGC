文档性质：**设计方案**（未来要实现的规则与算法基线），不是现状文档。这一点与《数据判定规则与算法说明》系列相反——那套文档只记录已上线的实际口径，本文用于迭代讨论，落地后再按实现情况沉淀回"现状文档"。

## 0. 已确认与默认决策一览

三个关键口径已确认（2026-08-15）：

| 决策项 | 结论 | 直接后果 |
|---|---|---|
| SPU 粒度 | **款型级**（车系+年款/动力/配置） | 主数据按款型建库；因内容文本大多只提车系，必须内置"车系兜底节点"与款型细化算法，并把**款型细化率**作为一等质量指标 |
| 关联判定方式 | **规则+LLM 双轨** | 规则词表为主链路（可复算、可版本化）；LLM 只处理未命中与灰区，输出必须带证据片段并经人工确认后落库 |
| 统计粒度 | **直接三维明细** | 以 SPU×人群×场景 明细表为统计基座；单维/二维榜单全部由明细 group by 派生；稀疏组合用小样本状态标注，不做榜单 |

本文另做了以下**默认决策**（未与业务确认，均可迭代推翻）：

| 默认决策 | 内容 | 依据 |
|---|---|---|
| D1 主SPU唯一 | 一条内容可命中多个 SPU，但统计默认只认"主SPU"（证据分最高者），次SPU 仅存明细 | 与现有主卖点/次卖点机制同构（v8.2 §6.5） |
| D2 实测与先验分离 | 内容的"实测场景"（文本证据直判）与"先验场景"（经 SPU→人群→场景 规则推出）**分开存储，统计默认只用实测**；两者对比构成 gap 分析 | 若统计直接采用先验场景，统计结果就是规则本身的同义反复，没有信息量 |
| D3 款型未细化兜底 | 只落到车系、落不到款型的内容，归入该车系的"未细化"兜底节点，不强行摊派到某个款型 | 与现有"缺失就是缺失、不补 0"的口径一致（v8.2 §20） |
| D4 场景多值命中即计 | 一条内容可命中多个场景，统计按"命中即计"；跨场景求和会大于内容总数，报表必须带脚注 | Kimball 多值维度桥接表标准口径（见 §2.3） |
| D5 阈值继承 | 确认阈值 75 分、灰区 60–74 分、证据封顶 V3=100/V2=90/V1=74，全部继承卖点链路数值 | 减少新体系的独立参数，先复用已校准的经验值 |
| D6 术语避让 | 本体系的"消费场景"统一称**用车场景**（S 码），避免与现有"三个业务场景"（二手车/新车/媒体-AI小懂，即内容方向）混淆；"目标人群"（P 码）避免与评论侧 `audience-classifier`（互动用户分类）混淆 | 现有系统术语已占用 |

## 1. 文档目的与范围

目标：建立"汽车SPU → 面向什么目标人群 → 该人群存在哪些用车场景"的三层规则资产，把规则与库内已有的有效内容关联起来，并统计每个 SPU / 人群 / 场景（及三维组合）的数据表现，首期只覆盖两个指标：**发布条数、曝光量**。

范围内：规则资产的数据结构与版本化、内容关联算法（规则链路+LLM辅助链路，无人工复核，见 §4.3 修订版）、统计口径与门槛、冷启动步骤、迭代路线。

范围外（首期不做）：互动/线索类指标、评论侧人群验证、款型级投放建议、对外报告形态。

与现有系统的关系：这是一套**独立的新维度体系**，不修改卖点词表和七项渠道指标；但机制上最大化复用 v8 已验证的三件套——词表版本化（taxonomy_versions 模式）、证据等级 V0–V3、指标快照口径（v8.5）。（原稿第四件"人工复核队列"随 §4.3 口径取消；schema v16 已删除全系统复核域。）

### 2.2 用车场景体系

平台方法论：懂车帝八大人群白皮书本身就把人群绑定到场景（通勤、全家出行、越野、露营、商务载货等）【二手】；小红书汽车打法以生活化场景笔记为主（提车日记、床车露营、车载好物、自驾、婚车、宠物出行）【二手】。车企实践：坦克300 绑定越野+露营+改装（越野SUV市占 68%）、理想绑定家庭场景（六座+宠物模式）、五菱绑定代步/摆摊创富/露营（五菱之光EV）、比亚迪以对外放电绑定露营户外用电【均有公开报道】。理论框架：JTBD（用户"雇佣"车完成任务）、麦肯锡消费者决策旅程、Google 汽车 5 个 micro-moments（which-car-is-best / is-it-right-for-me / can-I-afford-it / where-to-buy / am-I-getting-a-deal）【一手】、吴声《场景革命》。

由此汇总的**行业常见用车场景清单**（v0.1 场景词表的来源基础，逐条出处见 §10）：通勤代步、家庭出行/亲子、自驾游/长途、越野穿越、露营/车宿、商务接待/载货、网约营运、拉货/摆摊创富、宠物出行、改装玩车、新手练手。其中"新手练手"仅有社区口径（弱来源）；"女性用车"在多个来源中出现，但它是人群属性不是场景，本方案把它放入人群显式信号而非场景表。

## 3. 三层规则资产定义

规则资产分三件：**SPU 主数据库**（客观层）、**SPU→人群映射**（业务层）、**人群→场景映射**（业务层）。三件各自独立版本化，任何一件升版都触发关联结果增量重算（机制同卖点词表）。

### 3.1 SPU 主数据（款型级）

层级采用行业通行口径"品牌 → 车系 → 款型"（汽车之家/懂车帝车型库均为此结构；电商语义下 SPU≈车系、SKU≈款型，本项目按已确认口径直接建到款型级，同时保留车系层做兜底与上卷）。

```sql
CREATE TABLE spu_catalog (
    spu_id        TEXT PRIMARY KEY,   -- 稳定编码，如 byd__qin-plus__2026-dmi-55km-lead
    brand         TEXT NOT NULL,      -- 比亚迪
    series        TEXT NOT NULL,      -- 秦PLUS
    series_slug   TEXT NOT NULL,      -- 车系稳定键 byd__qin-plus
    trim_label    TEXT,               -- "2026款 DM-i 55KM 领先型"；车系兜底节点为 NULL
    is_series_node INTEGER NOT NULL DEFAULT 0,  -- 1=车系兜底节点（每车系有且仅有一个）
    model_year    INTEGER,            -- 2026
    powertrain    TEXT,               -- ev / phev / erev / hev / ice
    body_style    TEXT,               -- 轿车/SUV/MPV/皮卡...
    price_low     REAL,               -- 指导价下限（万元）
    price_high    REAL,
    external_ref  TEXT,               -- 懂车帝车系/车型 ID（可选，便于将来对库）
    enabled       INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE spu_alias (
    alias       TEXT NOT NULL,        -- 匹配词
    alias_type  TEXT NOT NULL,        -- official / nickname / slang / model_code
    spu_scope   TEXT NOT NULL,        -- series（指向车系）/ trim（指向具体款型）
    spu_id      TEXT NOT NULL REFERENCES spu_catalog(spu_id),
    ambiguous   INTEGER NOT NULL DEFAULT 0,  -- 1=歧义词（如"汉""星越"），必须过语境消歧
    enabled     INTEGER NOT NULL DEFAULT 1
);
```

要点：

1. **车系兜底节点**：每个车系建一条 `is_series_node=1、trim_label=NULL` 的记录。内容只提到"秦PLUS"落不到具体款型时，主SPU 指向兜底节点，统计中显示为"秦PLUS（未细化）"。这是 D3 决策的载体，避免款型级建库导致大量内容无处可归。
2. **别名表是识别召回的唯一来源**：官方名（秦PLUS DM-i）、民间俗称（大狗、陆巡、床车圈黑话）、型号代码（LC300）分类型维护。行业先例：哈弗大狗/欧拉好猫等官方昵称化命名与陆巡=兰德酷路泽等民间俗称并存，别名归一是车型实体识别的主要难点（汽车之家知识图谱用同义词识别+共现聚类处理）。
3. **歧义词标记**：与常用词/人名/地名撞车的别名（汉、唐、宋、海豹、星越、影豹…）标 `ambiguous=1`，命中后必须通过 §4.2 的语境消歧才能确认。
4. 建库范围**不追求全量车型库**：只建库内内容实际涉及的品牌车系（冷启动时先粗扫圈定，见 §7），控制维护成本。

### 3.2 人群维度与 SPU→人群 映射

人群维度 v0.1 以**抖音汽车八大人群为骨架**（P1–P8），字段含对照映射便于跨平台解读：

| 码 | 名称 | 定义要点（转述自白皮书报道，启用前核对原文） | 内容侧显式信号示例 |
|---|---|---|---|
| P1 | 生活精算师 | 关注油耗、保养、残值等全周期成本，拒付品牌溢价 | 油耗/电耗实测、养车成本、保值率、落地多少钱 |
| P2 | 摩登青年客 | 重性能、配置、智能化，视车为社交表达 | 零百、弹射、外观改色、氛围感 |
| P3 | 潮奢精质族 | 追求高端品质与品牌调性 | 豪华感、行政、气场 |
| P4 | 优价品质流 | 预算内追求品质均衡 | 性价比、同价位、值不值 |
| P5 | 温馨生活家 | 家庭用户；全家出行/亲子/长途返乡 | 宝妈、带娃、二胎、家用、六座 |
| P6 | 科技先锋派 | 智驾、智能座舱尝鲜 | 智驾、城市NOA、激光雷达、车机 |
| P7 | 野趣体验官 | 越野/露营户外；细分硬核探险家与露营漫游者 | 越野、穿越、露营、车宿、床车 |
| P8 | 实干奋斗者 | 营运与创富用途 | 跑网约、拉货、摆摊、回本 |

```sql
CREATE TABLE audience_dim (
    code TEXT PRIMARY KEY,            -- P1..P8
    label TEXT NOT NULL,
    definition TEXT NOT NULL,
    explicit_signals_json TEXT NOT NULL,  -- 内容侧显式身份/意图词表
    ref_mapping_json TEXT NOT NULL        -- 对照：小红书七类 / 贝恩八类
);

CREATE TABLE spu_audience_map (
    scope       TEXT NOT NULL,        -- series / trim
    scope_key   TEXT NOT NULL,        -- series_slug 或 spu_id
    audience_code TEXT NOT NULL REFERENCES audience_dim(code),
    role        TEXT NOT NULL,        -- primary（1个）/ secondary（≤2个）
    weight      REAL NOT NULL,        -- primary=1.0，secondary=0.5（v0.1 定值）
    basis       TEXT NOT NULL         -- 制定依据（研报/白皮书/评审记录）
);
```

映射的制定方法（不是拍脑袋）：按车型定位四要素（价格带 × 能源形式 × 车身形式 × 官方定位话术）套用白皮书人群特征，交叉核对罗兰贝格五大购车导向与公开车主画像报道，人工评审定稿并在 `basis` 里写明依据。**映射默认配置在车系层、款型自动继承**；仅当同车系款型定位差异显著时（坦克300 城市版 vs 越野版）在款型层覆盖。

### 3.3 场景维度与 人群→场景 映射

场景维度 v0.1（S1–S11，来源见 §2.2；"女性用车"归入人群显式信号不设场景）：

| 码 | 场景 | 触发词示例 | 负向词示例 |

## 4. 内容关联算法

### 4.1 输入与有效内容门槛

- 文本证据源 = 标题 + 正文 + ASR + OCR（与卖点链路一致；正文匹配同样去话题标签）；
- 参与关联的"有效内容" = `published_at` 非空的全部内容（发布条数口径）；
- **自动关联出结论需要证据等级 V2/V3**；V0/V1 不出自动结论、标待补证（继承 v8.2 §5 口径：证据不足不是"没有"）；
- 关联结果按 `(内容, evidence_sha256, 三件资产版本, association-v1)` 唯一，证据或任一版本变化才生成新结果，旧结果 `invalidated_at` 置位不删除。

### 4.2 规则链路（A 链，主链路）

**第一步：SPU 识别（两段式：词典召回 → 语境消歧 → 款型细化）**

```text
召回：
  用 spu_alias 全量别名构建 AC 自动机，对"标题+正文+ASR+OCR"单遍扫描
  → 候选集合 {(alias, spu_scope, spu_id, 来源通道, 次数)}

消歧（对 ambiguous=1 的别名逐个执行，非歧义词直接通过）：
  确认条件（满足其一）：
    a. 同一文本通道内出现该车系品牌词或厂商词（"比亚迪汉"）；
    b. 别名 5 字符窗口内出现车型限定词（DM-i、EV、冠军版、2026款…）；
    c. 全文含 ≥2 个汽车语境词（试驾/续航/油耗/落地价/提车…）且无强干扰语义。
  未过消歧的候选直接丢弃，不进灰区。

评分（对每个存活车系候选）：
  spu_score = 来源分 + 频次分 + 唯一性分 + 语境分，封顶按证据等级
    来源分：别名出现在 ASR/OCR：V3 30 / V2 24；仅标题 18；仅正文 12
    频次分：提及 ≥3 次 20；2 次 14；1 次 8
    唯一性分：全文唯一车系 25；多车系但该车系在标题或首段主叙事 18；其余 8
    语境分：品牌/厂商词同现 15；购车语境词（价格/试驾/对比/提车）10；上限 25
    封顶：V3 100 / V2 90 / V1 74（继承 D5）
  判定：≥75 确认；60–74 灰区 pending_review；<60 丢弃
  主SPU = 最高分候选；同分按 series_slug 字典序（确定性，同卖点链路）

款型细化（仅对已确认车系执行）：
  证据类型：年款词（2026款/26款）｜动力标识（DM-i/四驱/Max/55KM/510KM…）
           ｜配置名（领先型/智驾版…）｜价格锚（文本价 ∈ 某款型指导价 ±5%）
  命中款型候选唯一 → resolved_level=trim，主SPU 指向该款型
  多候选 → 取命中证据类型数最多者；仍并列 → 回退车系兜底节点 + 细化灰区标记
  零命中 → resolved_level=series，主SPU=车系兜底节点（D3）
```

对比样式内容（X1 类横评）会确认多个车系：全部保留为 SPU 关联明细（`is_primary=0`），仅主SPU 进默认统计；"对比内容是否应双计"列入开放问题 Q3。

**第二步：场景识别（实测场景）**

场景词表用 matcher DSL 直判，可多值。每个场景分数 = 来源分 + 频次分（同上取值），≥60 确认为实测场景；负向词命中则该场景直接否决。场景识别**不要求已识别出 SPU**——"无车系的泛露营用车内容"同样计入 S5 场景统计（SPU 维度为空桶）。

**第三步：人群归因（双通道）**

```text
通道① content_explicit：audience_dim.explicit_signals 命中（宝妈/新手/跑网约…）
       → 归因该人群，attribution_source='content_explicit'
通道② rule_prior：无显式信号时，主SPU → spu_audience_map 的 primary 人群
       → attribution_source='rule_prior'
优先级：content_explicit > rule_prior；
两通道同时存在且不一致 → 取 content_explicit，置 conflict_flag=1（只打标不改判，
   高频冲突是"SPU→人群映射错了"的直接信号，由人看板上的冲突计数驱动改规则）；
无主SPU 且无显式信号 → 人群为空，不强行归因。
```

**第四步：一致性检查（只打标不改判）**

实测场景 ∉ 归因人群的 core∪related 场景集合 → `consistency_flag=1`。该标记不影响任何统计，只进"规则外溢看板"（§5.5），作为修正 audience_scene_map 的证据。

### 4.3 LLM 辅助链路（B 链）——2026-08-16 修订：无人工复核版

> 口径修订（Mark 2026-08-16 确认）：本系统没有、也不会有"人工复核"这个
> 环节，原稿"LLM 结果一律进人工复核队列 + 抽检准入"的设计不成立。改为

触发条件（规则链跑完后，任一维度未解决即送判定）：a) 规则未识别出任何
SPU；b) SPU 处于灰区（60–74）；c) 车系已确认、款型库有该系款型但细化失
败；d) 场景或人群缺失。模型固定 `doubao-seed-2-1-pro-260628`（火山方舟
OpenAI 兼容接口，key 读 `DcarKey/dcar.env.local` 的 PROJECT_CLASSIFIER_*，

四道自动闸（全部通过才落库，实现见 `llm_assist.validate_judgement`）：

1. **闭集选择**：车系/款型/场景/人群只能从提示词携带的候选清单里选 id，
   清单外判定直接丢弃；"库外新车系"只累计计数进运行摘要，提示扩库；
2. **原文证据校验**：每项判定必须附 channel（title/body/asr/ocr）与 quote，
   程序逐字核对 quote 存在于发给模型的对应通道文本中，对不上即丢弃
   （零成本防幻觉，依据快手证据链实践与 arXiv 2410.13047 的引证要求）；
3. **置信度门槛**：<0.7 丢弃；灰区反向改判需 ≥0.8；
4. **规则优先**：规则明确命中（confirmed ≥75）的车型/场景/人群 LLM 一律
   不推翻；LLM 只补空白、裁灰区（同向→升级确认；反向高置信→按 LLM 落新
   行并在证据里记冲突）、在已确认车系的款型闭集内细化。

落库与回滚：LLM 行写现有三张 links 表，`rule_version='spu-llm-v1'`，
evidence_json 带模型名/置信度/引文通道/原文引文，运行摘要句披露"大模型
补充 N 处"；回滚 = CLI `--rollback-llm`（或 UPDATE 三张表 SET
invalidated_at 当前时间 WHERE rule_version='spu-llm-v1' AND invalidated_at
IS NULL）后重新刷新。

成本控制：判定按 (content_id, 截断文本哈希, 模型, prompt 版本) 缓存进
`llm_judgements` 表——规则重算后文本未变的内容直接重放缓存判定（含拒绝
判定），不重复调用付费；批跑先 `--llm-limit 100` 小样本验证质量与 token
用量再放量。

离线词表蒸馏（降级为副产品，不自动回填）：从判定结果聚合高频"库外新车
系"与场景表达进运行摘要供参考；词表修订仍走页面人工编辑——错词自动回填
会静默污染规则链，不做。

## 5. 统计口径（发布条数 + 曝光量）

### 5.1 数据结构：星型 + 桥接

事实 = 内容（发布事件）；维度 = SPU（款型级，含车系/品牌上卷）、人群、场景、平台、时间窗。内容↔SPU 与 内容↔场景 是多对多，走桥接表（content_spu_link / content_scene_link / content_audience_attribution，均带版本与失效字段）。统计不物化全量立方体，SQLite 直接 group by 派生。

### 5.2 三维明细表（统计基座）

```text
维度键：(platform, window, spu_id, audience_code, scene_code)
   spu_id：款型或车系兜底节点；未识别 SPU 记入 spu_id='__none__' 空桶
   audience_code：P1..P8 或 '__none__'
   scene_code：S1..S11 或 '__none__'
生成规则（每条有效内容展开为行集合）：
   {主SPU 或 __none__} × {归因人群 或 __none__} × {每个确认实测场景，无则 __none__}
度量：
   posts   = 该组合下去重内容条数
   views   = 该组合下内容最新快照 view_count(>0) 之和
附注列：
   audience_source 占比（content_explicit / rule_prior）
   resolved_level 占比（trim / series）
   low_sample = posts < 5
```

口径声明（必须随表输出）：

1. 主SPU 唯一、人群唯一（或空）、场景多值——**跨场景把 posts 求和会大于内容总数**（一条内容可同时是 S2 和 S3）；对账口径：任何上卷都按内容去重后再计数，去重总条数恒等于发布总数，分场景行直接求和只能 ≥ 总数，报表脚注写明（D4，Kimball 桥接口径）；
2. 空桶行保留（`__none__`），保证任何单维上卷都能与总量对账，同时把"未归类"的规模显性化；
3. 单维榜（SPU榜/人群榜/场景榜）与二维交叉全部由明细 group by 得出，不另建口径。

### 5.3 指标定义（全部继承现有口径）

- **发布条数**：窗口内 `published_at` 非空内容数；北京时间窗口、左闭右开、缺日期不入窗（v8.2 §3.1–3.2）；
- **曝光量**：每条内容按 `captured_at DESC, id DESC` 取最新快照的 `view_count`；仅 >0 有效；最新快照缺曝光不回退旧值（v8.5 §1）；数值是**抓取时累计值**，不是区间日终值——解读约束原样继承；
- 一条内容的曝光在其命中的每个组合行中**全额重复计入**（不按场景数摊薄）；如需"分摊口径"另加权重列，列入开放问题 Q4。

### 5.4 发布门槛与状态

沿用状态机 available / below_threshold / sample_only / not_applicable / missing：

| 检查 | 规则 |
|---|---|
| 条数类 | 有内容即 available，同时旁注归类覆盖率（=已归 SPU 内容 ÷ 总内容；已归人群、已归场景同理分列） |
| 曝光类 | 按平台×窗口计算"可归类曝光覆盖 = 已归SPU且有效曝光的曝光和 ÷ 有效总曝光"，≥90% 才 available，否则 below_threshold 且不出数（继承 v8.5 §4 按曝光量设门槛的设计：避免未归类爆款被低曝光长尾掩盖） |
| 组合行 | posts<5 标 low_sample，榜单默认过滤、明细导出保留 |
| 自动关联覆盖 | V2/V3 评估覆盖 <95% 时整表标 sample_only（继承评估覆盖门槛思想） |

### 5.5 预期 vs 实测：gap 分析（本方案把"规则"变成可统计资产的关键）

规则链 SPU→人群→core 场景给出**预期矩阵**（这款车的内容应该出现在哪些场景）；内容证据给出**实测矩阵**（实际发了什么、曝光在哪）。两者对比输出两张看板：

1. **覆盖缺口**：预期 core 场景中 posts=0 或曝光占比垫底的组合 → 选题机会（如：坦克300 预期 S4/S5，实测 S5 露营条数为 0）；
2. **规则外溢**：consistency_flag 聚集的组合（实测大量出现但映射表没写）→ 要么改 audience_scene_map，要么发现了新人群玩法。

这是 D2 决策的直接回报：统计不是验证规则的同义反复，而是校准规则的证据源。

「迭代点」①low_sample 阈值 5 是起步值；②曝光 90% 门槛对新维度可能过严（冷启动初期大概率 below_threshold），可考虑增设"披露覆盖率的样本口径展示"过渡态；③曝光是否按场景数分摊。

## 7. 冷启动与实施步骤

1. **粗扫圈库**：用一份临时品牌+车系词表（无需款型）对存量全部有效内容跑 AC 扫描，得出内容实际涉及的车系及条数分布；

3. **LLM 离线挖词**：对粗扫未命中但含汽车语境词的内容批跑 LLM，归纳别名/俗称/场景表达，人工校正后入词表；
