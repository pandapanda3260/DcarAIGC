## 0. 一句话需求

建设一条稳定、完整、及时、准确、可恢复、可追溯、成本可控的视频数据抓取链路，使计划账号的新视频能够被及时发现，互动指标能够持续更新，任何字段都能说明来源和更新时间，任何失败都能定位和恢复，所有业务页面和报表使用同一份可信数据。

## 1. 需求背景

当前系统已经能够从 Matrix、TikHub 和部分抖音开放平台能力中获取视频数据，也已经具备账号名册、定时任务、原始响应留存、数据库写入、指标更新和业务报表等能力。

但专项审计确认，现有链路仍存在以下业务问题：

1. 新视频发现不够及时，部分内容需要十几个小时甚至更久才能进入系统。
2. 定时抓取会反复扫描大量窗口外历史视频，耗时、耗费额度，并拖慢新视频发现。
3. 不同接口返回同名字段时，系统不能准确判断应该信哪一个，已经出现分享数明显错误。
4. 一个失败账号或失败视频可能长期占住任务队列，影响其他正常账号。
5. 服务重启、数据库锁、接口限流或进程异常后，部分任务不能自动、准确地恢复。
6. 视频删除、私密、地域限制、接口暂时失败目前没有被清楚区分。
7. 数据库虽然有抓取时间，但不能完整回答某个字段什么时候抓到、什么时候成功更新、现在是否过期。
8. 当前不能稳定计算视频完整率、字段准确率、失败恢复时间和真实积压。
9. 健康检查和日志不足以在故障发生时快速定位到具体平台、账号、视频和错误原因。
10. 列表、报表、导出和下游分析存在读取到不同口径数据的风险。

因此，本次改造的核心不是“增加抓取量”，而是让抓取结果真正具备业务可用性和生产可控性。

## 2. 建设目标

### 2.1 业务目标

1. 计划账号发布新视频后，系统能够在明确 SLA 内发现。
2. 视频互动数据根据发布时间和业务价值持续更新。
3. 所有业务字段都有明确、统一的可信来源。
4. 单个账号、平台或接口失败不会阻塞其他正常任务。
5. 中断和失败能够自动恢复，无法自动恢复时进入明确的待处理状态。
6. 视频删除、私密、受限和技术失败能够被准确区分。
7. 运营、报表和分析使用同一份数据口径。
8. 能够量化完整率、成功率、准确率、重复率、延迟、积压和费用。
9. 任一异常都可以追溯到原始响应和具体任务。
10. 每次上线都能够证明当前运行的确实是经过审批和验收的版本。

### 2.2 成功标准

- 视频发现延迟 P95 不超过 60 分钟，P99 不超过 2 小时。
- 日最终抓取成功率不低于 99.5%。
- 日视频完整率不低于 99.5%。
- canonical 视频重复率为 0。
- 结构字段准确率不低于 99.9%。
- 互动计数字段准确率不低于 98%。
- 失败恢复时间 P95 不超过 15 分钟，P99 不超过 60 分钟。
- 并发、故障注入和受控上线验证中，不得出现数据库锁导致的任务失败、SIGBUS 或僵尸任务。
- 所有业务使用方读取同一数据投影和字段口径。

## 3. 需求范围

### 3.1 本次范围

#### 平台范围

- 抖音
- 小红书

#### 账号范围

- 系统 accepted roster 中的全部有效账号
- 当前规划规模约 325 个账号
- 每轮任务必须冻结当时的账号范围，执行中不能偷偷改变分母

#### 数据范围

- 视频身份
- 视频链接
- 账号身份和账号关联
- 标题、正文、内容类型
- 视频发布时间
- 播放数
- 点赞数
- 评论数
- 收藏数
- 分享数
- 视频公开、私密、删除和受限状态
- 每个字段的数据来源、抓取时间和新鲜度

#### 流程范围

- 新视频发现
- 视频详情抓取
- 指标更新
- 失败补偿
- 历史断档补抓
- 手工刷新
- 原始响应留存
- 数据解析和写入
- 字段可信选择
- 数据质量检查
- 后台运行监控和异常记录
- 列表、报表、导出和下游使用

### 3.2 不在本次范围

- 新增微信视频号、快手或其他新平台的自动抓取。
- 改造视频下载、OCR、ASR、内容理解、卖点提取和标签生成逻辑。
- 增加游客网页抓取、登录态复用或绕过授权的采集方式。
- 对全部历史数据重新进行无预算付费抓取。
- 重做整个内容管理前端。
- 新增弹窗、提示框、预警文案、状态角标、Toast、红点或主动通知。
- 为展示抓取状态而增加新的业务页面信息；本次改造保持现有业务页面交互和字段展示不变。
- 修改业务报表本身的统计含义。
- 将测试通过、代码提交或服务重启视为生产改造完成。

## 4. 用户角色和核心场景

### 4.1 内容运营

内容运营需要：

- 及时看到账号新发布的视频。
- 能够对指定视频发起一次受控更新。
- 不能因为重复点击产生重复请求或重复费用。

### 4.2 报告和数据使用者

报告和数据使用者需要：

- 列表、日报、周报、CSV、Excel 和分析结果使用相同字段值。
- 报告能够说明使用了哪个数据版本和截止时间。
- 后续数据修复不能静默篡改已经发布的历史报告。

### 4.3 值班和运维人员

值班人员需要：

- 快速判断系统是否正常运行。
- 查看具体哪个平台、账号、视频或接口失败。
- 知道失败是否会自动重试、何时重试。
- 能够查看积压、熔断、授权、预算和死信任务。
- 在不修改数据库的情况下安全重试指定任务。

### 4.4 管理员

管理员需要：

- 管理账号范围和账号授权状态。
- 管理 provider 和 operation 的费用预算。
- 暂停异常数据源或历史任务。
- 审批历史补抓和死信重放。
- 查看操作记录和实际影响范围。

### 4.5 开发、测试和审计人员

开发和审计人员需要：

- 使用已经保存的 raw response 重放解析和字段选择。
- 不调用真实接口就能验证修复结果。
- 能够从业务字段追溯到 observation 和 raw。
- 能够区分需求已评审、代码已实现、测试已通过和生产已发布。

## 5. 统一业务口径

### 5.1 视频身份

- 视频唯一身份必须是 `平台 + 平台视频 ID`。
- URL 只能作为检索和辅助归一化依据，不能替代平台视频 ID。
- 同一个视频被多个来源重复发现时，只能对应一条 canonical 内容。
- 平台视频 ID 缺失时必须明确标记，不能随意生成一个看似真实的 ID。

### 5.2 时间

必须明确区分：

| 时间 | 含义 |
| --- | --- |
| 视频发布时间 | 视频在平台发布的时间 |
| 平台数据时间 | 平台明确说明互动数据所属的时间点 |
| 请求开始时间 | 系统发出接口请求的时间 |
| 响应完成时间 | 系统完整收到接口响应的时间 |
| 原始数据抓取时间 | Raw response 固定完成的时间 |
| 数据库记录时间 | Observation 写入数据库的时间 |
| 字段成功更新时间 | 某个业务字段最后一次成功更新的时间 |
| 下次计划更新时间 | 该账号或视频下一次应执行的时间 |

统一要求：

- 数据库存储统一使用 UTC。
- 业务日、定时任务和页面展示使用 `Asia/Shanghai`。
- 所有时间窗口使用左闭右开 `[start, end)`。
- 平台没有提供数据时间时必须保持为空，不能用抓取时间冒充。
- 播放、点赞、评论、收藏、分享可能来自不同时间，不能只返回一个含混的“更新时间”。

### 5.3 字段状态

每个字段必须能够区分：

- `fresh`：数据在目标更新时间内。
- `stale`：有历史值，但已经超过目标更新时间。
- `missing`：接口应该提供但当前没有值。
- `invalid`：值不合法或解析失败。
- `not_applicable`：该平台不提供或不适用。
- `conflicted`：多个可信来源存在无法自动解决的冲突。
- `regression_suspected`：数值下降，需要后续确认。

“没有返回”“不适用”“真实为 0”和“暂时失败”不得混为同一种状态。

## 6. 详细需求

### REQ-001 账号和任务范围必须可证明（P0）

系统必须做到：

1. 每轮抓取开始前冻结账号名单、平台、时间窗口、来源策略和计划数量。
2. 执行过程中账号名单变化不能改变本轮完成率分母。
3. 当前任务和历史任务必须分开统计。
4. 无法确认实际账号范围时，不得把任务标记为完整成功。
5. 运营和审计人员可以查看本轮原计划抓取哪些账号。

验收标准：

- 计划账号数与创建的账号任务数一致。
- 任一任务都可以还原账号范围和时间范围。
- 范围未知时，完整率检查必须失败。

### REQ-002 数据源是否可用必须经过真实验证（P0）

系统必须做到：

1. 区分“代码里存在接口客户端”和“当前账号实际有权限使用”。
2. 只有完成真实权限、分页、字段和 Token 刷新验证的数据源才能进入正式路由。
3. Matrix、Douyin OpenAPI、TikHub 的可用状态必须按平台、账号和 operation 记录。
4. 某个数据源不可用时，系统必须说明回退原因。
5. 不得因为数据源返回空结果就直接认为账号没有视频。

验收标准：

- 每次外部请求都能说明为什么需要调用。
- 未验证的 OpenAPI 账号不计入发现 SLA。
- 连续异常空结果必须在后台记录为异常，不能计为成功。

### REQ-003 新视频必须及时发现（P0）

系统必须做到：

1. Accepted roster 中的有效账号必须周期性检查新视频。
2. 每个账号独立执行，一个账号失败不能阻塞其他账号。
3. 新视频发现后至少保存平台视频 ID、账号 ID、发布时间、链接、来源和抓取时间。
4. 相同视频重复发现不能生成第二条 canonical 内容。
5. 主来源断档时必须及时触发补偿来源。

验收标准：

- 视频发现延迟 P95 ≤60 分钟。
- 视频发现延迟 P99 ≤2 小时。
- canonical 视频重复率为 0。
- 单账号失败时，其他正常账号仍在两个周期内完成发现。

### REQ-004 增量抓取不得反复翻完整历史（P0）

系统必须做到：

1. 记录每个账号上一次完整成功抓取到的位置。
2. 下一轮从上次成功位置附近继续，并保留必要重叠范围防止漏数。
3. 只有完整成功的任务才能推进成功位置。
4. Partial、超时、解析失败和分页异常不得推进。
5. 当页面内容已经明确早于目标范围时必须停止翻页。
6. 置顶内容、乱序、重复 cursor 和时间缺失必须被识别。
7. 单个账号处理时间过长时必须让出执行资源，不能拖住整轮。

验收标准：

- 正常增量任务不再持续翻取窗口外历史数据。
- 重复执行同一范围不会新增重复内容。
- 分页异常不会导致水位错误推进。
- 历史扫描不会阻塞新视频发现。

### REQ-005 视频详情和指标必须分层更新（P0）

更新频率要求：

| 视频发布时间 | 核心指标更新频率 | P95 更新延迟 |
| --- | --- | --- |
| 0–2 天 | 每 2 小时 | ≤2.5 小时 |
| 3–7 天 | 每 6 小时 | ≤7 小时 |
| 8–30 天 | 每 24 小时 | ≤26 小时 |
| 31–90 天 | 业务活跃内容每 7 天 | ≤8 天 |
| 超过 90 天 | 按需、报告或受控历史任务 | 由任务合同确定 |

补充要求：

1. 评论数属于核心指标。
2. 评论明细不是全局周期任务，只在审核、分析或明确业务任务中抓取。
3. 媒体下载、评论明细和内容分析失败，不能回滚已经成功的视频发现和指标更新。
4. 已有新鲜字段不能因为其他字段缺失而被重复购买。

### REQ-006 每个业务字段必须有唯一可信来源规则（P0）

系统必须做到：

1. 按平台、数据源、接口 operation 和字段定义可信规则。
2. 同一个 provider 的不同 operation 不能被认为字段语义一定相同。
3. 未登记的新 operation 默认不能进入业务数据。
4. 空值、占位值、旧值和解析失败不能覆盖有效值。
5. `TikHub video_statistics.share_count` 不得继续进入 canonical 分享数。
6. 播放、点赞、评论、收藏和分享可以各自使用不同来源。
7. 每个字段必须在后台保留来源、operation、抓取时间和新鲜度，供数据校验和问题追溯使用，不要求业务页面新增展示。

验收标准：

- 已确认的两个 share 错误样本修复。
- 未认证 operation 进入 share canonical 的数量为 0。
- 所有字段路由测试命中率为 100%。

### REQ-007 字段冲突和数值下降必须被正确处理（P0）

系统必须做到：

1. 多个来源差异超过容差时标记为冲突。
2. 计数下降时保留新 observation，但不能直接假设旧值或新值一定正确。
3. 下降必须经过同一可信接口再次确认或第二可信来源确认。
4. 异常突增同样必须有检查机制。
5. 不得简单使用历史最大值掩盖平台真实数据修正。
6. stale、conflicted 或 suspected 状态只用于后台字段选择和质量校验，不新增业务页面提示。

验收标准：

- 异常 observation 全部保留。
- 一次异常接口响应不会静默污染 canonical。
- 开发和数据人员可以通过后台记录追溯冲突原因和确认动作。

### REQ-008 原始响应必须完整、不可变、可重放（P0）

系统必须做到：

1. 每次外部响应记录 provider、operation、账号/视频、HTTP 状态、计费状态和请求时间。
2. 原始响应保存文件路径、大小、SHA-256 和抓取时间。
3. 解析失败也必须保留 raw response。
4. Raw 和 observation 只能追加，不能覆盖。
5. Raw hash 不一致时不能进入业务投影。
6. 修复解析和字段规则时优先使用 raw replay，不重复付费。

验收标准：

- 抽检 raw hash 一致率为 100%。
- 任一 canonical 字段能够追溯到 observation 和 raw。
- 同一 raw replay 三次得到相同结果。

### REQ-009 重复执行必须幂等（P0）

系统必须做到：

1. 相同视频、页面、范围、任务和 raw 重复处理不会产生重复 canonical。
2. 进程重启后继续处理不能重复购买已经固定的 raw。
3. 手工更新重复点击不能创建重复付费请求。
4. 任务状态和数量必须守恒。

验收标准：

- 相同页面重放三次后 canonical 数量不变。
- 同一批 1,000 条视频以不同顺序重放，结果 hash 一致。
- canonical 重复率为 0。

### REQ-010 单个失败任务不得阻塞其他任务（P0）

系统必须做到：

1. 任务按账号、内容和 stage 独立运行。
2. 当前发现和近期指标优先于历史补抓。
3. 同一优先级内按账号公平轮转。
4. 单个失败账号、终态视频或历史任务不得长期占住队首。
5. 系统资源不足时应延后低优先级任务，而不是无限增加并发。

验收标准：

- 一个持续失败账号不会让其他账号超过两个调度周期未执行。
- 历史补抓运行时，新视频发现仍满足 SLA。
- 最老实时任务超过 30 分钟必须在后台记为积压异常，并停止继续扩大低优先级任务。

### REQ-011 任务失败必须自动恢复或明确进入待处理（P0）

系统必须做到：

1. 任务被 worker 领取后必须有 owner 和有效期限。
2. 任务执行中需要持续 heartbeat。
3. Worker 异常退出后，过期任务能够被自动回收。
4. 旧 worker 恢复后不能覆盖新 worker 结果。
5. 僵尸恢复必须周期执行，不能只在服务启动时执行。
6. 自动重试必须有上限，超过上限进入死信。

验收标准：

- Kill worker 后 6 分钟内任务重新可领取。
- 旧 owner 成功覆盖新结果的次数为 0。
- 失败恢复 P95 ≤15 分钟，P99 ≤60 分钟。

### REQ-012 重试必须按错误类型执行（P0）

系统必须做到：

1. 优先遵守 provider 返回的 Retry-After。
2. 瞬时网络错误、429 和 5xx 可以退避重试。
3. Token 失效只刷新一次，刷新失败后停止该账号并记录待重新授权状态，不新增提示信息。
4. 参数错误、权限未开通、内容删除和私密不得按网络错误无限重试。
5. 同一逻辑任务最多尝试 5 次。
6. 计费状态未知时不得立即重新购买。
7. Provider 连续失败时必须熔断，不能继续形成请求风暴。

验收标准：

- 错误分类准确率 100%。
- 不存在固定周期无限重试。
- 重试次数、时间和费用可以完整审计。

### REQ-013 达到重试上限的任务必须进入死信（P0）

系统必须做到：

1. 达到最大次数、raw integrity 错误、schema drift 和需要人工介入的任务进入 DLQ。
2. DLQ 保留原范围、所有 attempt、错误分类、最后 raw 和建议动作。
3. DLQ 不再进入普通队列。
4. 人工重放必须创建新的补偿任务，不能修改旧失败事实。
5. 补偿仍使用原冻结范围，不能自动扩大购买范围。

验收标准：

- 持续失败项不会继续占住普通队列。
- 任一 DLQ 项可以被定位、关闭或受控重放。

### REQ-014 历史断档必须可以独立补抓（P1）

系统必须做到：

1. 历史补抓开始前在任务记录中固化账号、窗口、预计页数、预计请求量、预计费用和预计完成时间。
2. 历史任务使用独立低优先级队列和预算。
3. 实时任务积压或预算不足时自动暂停历史任务。
4. 历史任务失败恢复不能扩大原窗口。
5. 历史结果和实时结果使用相同身份和字段规则。
6. 历史任务必须有明确 remaining、ETA 和终态收据。

验收标准：

- 现有历史 pending 工作可以持续推进。
- 历史运行期间实时发现和近期更新仍满足 SLA。
- 实际费用不超过批准预算。

### REQ-015 视频不可见状态必须可审计（P0）

系统必须做到：

1. 区分公开、疑似不可见、私密、删除、地域限制、版权限制和未知。
2. 一次列表缺失不能直接判删除。
3. 技术错误不能改变内容可见性。
4. 权威证据确认后才进入业务终态。
5. 后续公开证据可以恢复为公开状态。
6. 任何状态都不能物理删除历史内容、raw 或指标。

验收标准：

- 私密、删除、受限、临时错误和恢复公开测试全部正确。
- `unknown` 被错误判成 `deleted` 的数量为 0。

### REQ-016 数据更新时间和新鲜度必须按字段记录（P0）

系统必须做到：

1. 区分视频发布时间、平台数据时间、请求时间、抓取时间、写入时间和字段成功更新时间。
2. 播放、点赞、评论、收藏和分享分别计算新鲜度。
3. 数据过期时后台必须记录 stale，并禁止不可信旧值覆盖正确数据；不新增业务页面提示。
4. 平台未提供数据时间时必须明确为空。
5. 业务报告必须固定截止时间和数据版本。

验收标准：

- 任一字段可以回答“值是多少、来自哪里、什么时候抓到、现在是否过期”。
- 五个互动字段不再共用一个无法解释的更新时间。

### REQ-017 系统必须持续计算数据质量（P1）

系统必须计算：

- 账号范围守恒
- 分页数量守恒
- cursor 重复和排序异常
- 内容 ID、账号、发布时间、URL 缺失
- canonical 重复
- raw 文件缺失和 hash 不一致
- 未封口 attempt
- 指标负数、占位零、异常倒退和异常突增
- 字段来源冲突
- 视频完整率
- 最终成功率
- 数据新鲜度
- 字段准确率
- 费用和无结果请求比例

验收标准：

- 每日自动生成质量结果。
- 预置缺失、重复、回退、cursor 循环和 raw 损坏均能被检出。
- 质量异常不能修改原始 observation，只能阻止或回滚 canonical。

### REQ-018 后台监控和异常记录必须能定位到具体对象（P0）

系统必须监控：

- 任务计划量、领取量、运行量、成功量、失败量、DLQ 量
- 队列深度和最老任务年龄
- Provider 请求量、成功率、错误码、耗时、限流和熔断
- 账号和视频最后成功时间
- 视频发现延迟和指标更新延迟
- 完整率、重复率、字段冲突和字段准确率
- 数据库写入耗时、锁等待、WAL/IO 错误
- Provider 费用、剩余预算和单位产出成本

异常判定规则：

- Writer 退出、SIGBUS、数据库 IO 错误、15 分钟无成功进展：记录最高级别后台异常。
- 实时任务积压超过两个周期或 30 分钟：记录积压异常并暂停低优先级任务。
- 最终成功率或完整率低于 99.5%：记录质量异常。
- 字段出现大规模冲突、倒退或 raw integrity 错误：隔离异常数据并保留完整证据。
- 本期不建设弹窗、提示框、预警文案、主动通知或新的告警页面。

验收标准：

- 任一后台异常在 5 分钟内能够通过日志和任务记录定位到平台、provider、operation、账号、视频、任务和 raw。
- 数据库被锁时仍能留下独立异常证据。

### REQ-019 健康检查必须轻量且可靠（P0）

系统必须提供：

1. 进程存活检查，不访问数据库。
2. 就绪检查，只执行轻量数据库读取、执行器 heartbeat 和积压判断。
3. 深度 raw/hash/完整率检查，由后台周期执行并缓存结果。
4. 深度检查失败不能拖死进程存活检查。

验收标准：

- 存活检查 P95 <100ms。
- 就绪检查 P95 <500ms。
- Raw 规模增长时健康接口仍能稳定返回。

### REQ-020 所有业务使用方必须读取同一份可信数据（P0）

范围包括：

- 内容列表和搜索
- 内容详情
- Overview 和统计 API
- 单视频手工更新结果
- 日报和周报
- CSV/Excel 导出
- SPU audience
- 卖点、标签和其他指标调用方

要求：

1. 所有使用方使用同一 projection version。
2. 页面和导出不能自行重新拼接字段来源。
3. 过期、冲突和不可见状态必须参与后台字段选择，不能把错误值写入统一投影；业务页面不新增状态提示。
4. 历史报告修复生成新 revision，不能静默覆盖旧报告。

验收标准：

- 100 条业务回归样本在所有使用方的字段结果 100% 一致。

### REQ-021 手工更新必须安全、异步、幂等（P1）

系统必须做到：

1. 手工更新只创建受控任务，不在页面请求中直接抓 provider。
2. 返回明确的任务 ID 和状态。
3. 重复操作不创建重复付费请求。
4. 同样受账号范围、预算、缓存、限流、重试和字段权威规则约束。
5. 系统不可用时返回明确失败，不产生半任务。

验收标准：

- 同一更新指令重复提交只产生一个逻辑任务。
- 任务记录可以追溯进度、失败原因和最终数据版本，不新增进度提示框。

### REQ-022 授权和 Token 必须按账号管理（P0）

系统必须做到：

1. 记录每个账号实际具备的授权能力。
2. 同一账号同时只允许一次 Token 刷新。
3. Refresh 失败后停止该账号官方接口调用，并记录待重新授权状态，不新增提示信息。
4. 一个账号授权失败不得阻塞其他账号。
5. 未验证权限不得被标记成官方来源可用。
6. Token、Secret 和 Authorization header 不得进入日志。

验收标准：

- 授权生命周期测试全部通过。
- 凭据泄漏数量为 0。

### REQ-023 费用必须可归因、可限制、可停止（P0）

系统必须做到：

1. 每次付费请求归属于 provider、operation、账号、任务和 attempt。
2. 失败但计费的请求也计入预算。
3. 历史、评论、老视频和新视频发现分别统计费用。
4. 达到 85% 时暂停历史和低优先级任务。
5. 达到 100% 时停止所有非关键付费请求。
6. 新视频发现保留独立容量，但不能突破总硬上限。
7. 可以本地 replay 时禁止重新付费。

验收标准：

- 系统账本与 provider 账单差异 ≤1%。
- 预算耗尽后超额请求数量为 0。

### REQ-024 发布版本必须可证明（P0）

每次生产切换必须能够证明：

- 审批的是哪个 commit。
- 运行进程实际加载的是哪个 commit。
- 使用哪个 schema 和配置版本。
- 使用哪个字段规则版本。
- 正式数据库路径和 fingerprint 是什么。
- 进程何时启动、PID 是什么。
- 上线前通过了哪些测试和影子验证。
- 回滚版本和回滚耗时是多少。

验收标准：

- 运行 commit 必须等于审批 commit。
- 脏工作树构建不得切换生产。
- 任一发布收据缺失时禁止上线。

## 7. 非功能需求

### NFR-001 稳定性

- 日最终任务成功率 ≥99.5%。
- SQLite 并发测试和故障注入中，不得出现 lock 导致的任务失败。
- 故障注入和受控上线验证中不得出现 SIGBUS。
- 无任务丢失、无双 owner、无旧 worker 覆盖新结果。

### NFR-002 性能

- 325 个账号的任务计划在 60 秒内生成。
- 正常队列中，任务到期到开始执行 P95 <1 分钟。
- 存活检查 P95 <100ms。
- 就绪检查 P95 <500ms。
- 数据写入不能长时间阻塞业务查询。

### NFR-003 扩展性

- 账号、内容和日任务量扩大到当前 2 倍时仍满足核心 SLA。
- 30 分钟 3 倍峰值注入后，积压在两个周期内回落。
- 新 provider 必须通过统一字段合同和错误分类接入，不能复制一套独立调度系统。

### NFR-004 数据耐久性

- Raw 和 observation 不可变。
- 迁移前后数据行数、hash、FK 和 integrity 可以对账。
- 数据结构升级必须保留旧版本可读和回滚能力。
- 不允许通过删除 WAL、锁文件或历史记录解决故障。

### NFR-005 安全

- Token、密钥、Authorization header 不进入日志和错误详情。
- 生产、测试和回放环境凭据隔离。
- 自动测试禁止连接正式写库。
- 手工重试、预算调整、授权变化和数据纠正需要操作记录。

### NFR-006 可审计性

- 100% 外部请求具有任务和原始证据身份。
- 100% 任务状态变化可以还原。
- 100% canonical 抽样字段可以追溯 raw、operation、时间和规则版本。
- 报告 correction、人工 replay 和生产切换均有不可变收据。

### NFR-007 兼容性

- 现有 API 字段至少保留一个发布周期。
- 质量、来源和异常详情只通过后台追溯能力提供，业务 API 和页面不新增提示类字段。
- 现有列表、报表、导出和下游业务在切换前完成回归。

## 9. 验收范围

### 9.1 单元与规则验收

- 字段权威路由
- 时间和时区边界
- 增量范围和重复处理
- 分页停止和 cursor 异常
- 字段冲突和数值下降
- 错误分类和最大重试
- 授权生命周期
- 内容可见性状态
- 费用和预算守恒

### 9.2 完整链路验收

必须覆盖：

```text
账号范围
→ 新视频发现
→ 请求和原始响应
→ 解析和 Observation
→ 字段可信选择
→ Canonical
→ API
→ 列表、报表、导出和下游业务
```

### 9.3 故障验收

必须模拟：

- 429
- 5xx
- 请求超时和连接中断
- Token 失效和刷新失败
- Cursor 重复和乱序
- Raw 文件损坏
- 进程被杀死
- 数据库 busy/locked
- 磁盘不足
- Provider 中断一小时

### 9.4 三方金标

至少核验 100 条公开视频：

- 抖音 60 条
- 小红书 40 条
- 另设不少于 20 条私密、删除或不可见状态样本

要求在尽可能接近的时间内完成“平台可见值—接口 raw—数据库 canonical”三方记录。

通过标准：

- 身份、作者、发布时间、URL 和状态准确率 100%。
- 互动计数字段至少 98% 满足误差 `≤max(2,2%)`。
- Share 路由准确率 100%。

## 10. 完成定义

以下条件必须同时满足：

1. 所有 P0 需求已经实现并完成验收。
2. 所有 S0 和 S1 测试通过。
3. 自动化测试、raw replay、金标核对和受控上线验证达到发现、更新、成功率、完整率、准确率和恢复 SLA。
4. SQLite 并发、故障注入和受控上线验证中无 lock 任务失败、无 SIGBUS、无双 owner 和僵尸任务。
5. 已确认的两个 share 错误样本和新增金标全部通过。
6. 所有业务使用方读取相同 projection version。
7. 视频私密、删除、受限和技术失败可以被准确区分。
8. 历史任务和实时任务已经隔离，历史任务不再阻塞新视频。
9. 任何任务和字段都能定位到原始响应和失败原因。
10. 实际运行 commit、schema、配置和字段规则有完整发布收据。
11. 回滚演练完成，能够在 15 分钟内恢复安全版本。

需求评审通过不等于完成；代码合入不等于完成；测试通过不等于完成；进程重启也不等于完成。只有上述生产验收全部满足，才可以将“视频数据抓取链路改造”标记为完成。

## 11. 上线前必须进一步确认的事项

1. 当前 writer 实际加载的 commit。
2. SQLite 写事务串行化在真实负载下是否稳定。
3. Douyin OpenAPI 各账号当前实际权限、字段和额度。
4. Matrix 私有接口的正式字段、分页、配额和 Token 合同。
5. 小红书 App 可见数据的人工金标方式。
6. TikHub 当前价格、余额和计费边界。
7. 开发开始前的干净 commit 和未提交改动归属。

这些事项未确认前，需求可以评审，但对应生产能力不得宣称已经可用。
