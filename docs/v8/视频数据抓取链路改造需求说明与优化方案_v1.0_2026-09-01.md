# 视频数据抓取链路改造需求说明与优化方案

- 文档版本：V1.0
- 编制日期：2026-09-01
- 文档状态：待评审，Plan-only
- 适用项目：DCar Insight / DcarAIGC
- 适用平台：抖音、小红书
- 当前阶段：仅需求说明与优化方案，尚未实施
- 明确边界：本文档不代表代码已经修改、测试已经完成或生产已经发布

## 0. 执行摘要

当前视频数据抓取链路已经具备账号名册、Matrix/TikHub 接口封装、Douyin OpenAPI 授权控制、定时任务、fetch slot/attempt、预算账本、原始响应留存、不可变指标事实、业务投影以及报表消费等基础能力。

专项审计同时确认，当前链路仍存在四类会直接影响生产结果的问题：

1. SQLite 写争用和 WAL 运行稳定性问题，会同时影响抓取、调度、失败恢复和 API 查询。
2. TikHub 的“7 天窗口”没有真正成为分页停止条件，实际运行会反复翻取账号历史数据。
3. 指标选择器没有按照 `platform + provider + operation + field` 区分字段语义，已经出现错误分享数进入业务投影的情况。
4. 失败任务、历史任务和当前任务缺乏隔离、公平调度、租约、死信和周期恢复，容易长期占住普通队列。

本次改造不重写整个系统，也不引入 Kafka、Airbyte 或新的分布式数据库。唯一目标架构确定为：

```text
只读 API
  ↓ 本机 Unix Domain Socket 命令
单写 Capture Controller
  ↓ 创建账号级持久任务
有界 Provider Worker
  ↓ 固定 Raw Evidence
不可变 Observation
  ↓ 字段级权威路由
统一 Canonical Projection
  ↓
列表 / 报表 / 导出 / SPU / 卖点与标签业务
```

改造必须按照以下顺序执行：

1. 冻结运行版本，稳定 writer、SQLite 和发布边界。
2. 先修字段准确性，禁止错误 share 继续进入业务投影。
3. 拆分账号级任务，增加水位线、48 小时重叠、页级 checkpoint、lease 和 watchdog。
4. 增加分层更新、重试、熔断、DLQ、历史独立队列和费用优先级。
5. 补齐轻量健康检查、结构化日志、数据质量、费用和积压监控。
6. 通过自动化测试、raw replay、金标核对、故障注入和受控小流量验证后逐步切换生产。

只有全部 S0/S1 测试通过、SQLite 并发与故障注入验证通过、核心 SLA 全部达标、运行版本收据完整、回滚演练通过，才能将本次改造标记为完成。

## 1. 当前基线和证据边界

### 1.1 代码与运行边界

- 专项审计的主要代码基线为 `89c98b3`，对应交付 HEAD `06418b6`。
- 审计期间共享仓库被外部推进到 `c42c40c fix(v8): serialize sqlite write transactions`。
- writer 在审计期间由旧 PID 46987 重启为 PID 78951。
- 当前系统没有 `loaded_git_commit` 运行收据，不能只根据 HEAD 或进程启动时间证明实际加载版本。
- 重启后的短观察窗口没有新增 `database is locked`，但仍持续出现 `max_instances` 跳过。
- `/openapi.json` 可快速返回，但 `/api/v8/health` 和 `/api/v8/scheduler` 仍会在 5 秒内超时。
- 工作树存在与本需求文档无关的外部未提交改动，正式开发前必须建立干净的版本边界。

### 1.2 当前数据库与数据基础

- 正式库：`app/data/dcar_insight.sqlite3`
- 当前 schema：18
- 内容主记录约 79,972 条
- 内容身份唯一约束：`(platform, platform_content_id)`
- 已存在不可变 `content_metric_observations`
- 已存在 `provider_raw_responses` 及文件 SHA-256
- 已存在 `fetch_slots`、`fetch_attempts`、`scheduler_runs`、`scheduler_run_attempts`
- 已存在 provider 使用量和预算批次账本
- 抽验 raw 文件路径、文件大小和 SHA-256 与数据库一致
- canonical 内容 ID 和规范化 URL 重复均为 0

### 1.3 已确认问题

| 严重级别 | 问题 | 确认证据 | 已造成影响 |
| --- | --- | --- | --- |

| P0 | TikHub 窗口未限制分页 | 当前 7 天窗口 4,110 页、81,235 条 raw，其中 52,136 条在窗口外，只新增 657 条 | 付费放大、新视频延迟、父任务运行 7 小时以上 |

## 2. 建设目标

### 2.1 业务目标

1. 计划名册中的公开视频在发布后 60 分钟内被发现，极端情况下不超过 2 小时。
2. 视频指标按照生命周期分层更新，页面、报表和导出均读取同一可信投影。
3. 单账号、单平台、单接口、单字段或单批次失败不得阻塞其他工作。
4. 服务重启、进程崩溃、限流、Token 失效、数据库短暂不可用后能够自动恢复。
5. 能够直接计算完整率、最终成功率、重复率、字段准确率、新鲜度、恢复时间和积压年龄。
6. 每个业务字段可以追溯到 provider、operation、raw、observation 和选择规则。
7. 每次付费调用可以归因到任务、账号、operation、attempt 和预算批次。

### 2.2 技术目标

1. 查询 API 与抓取执行进程分离，API 不再持有正式库写权限。
2. 正式库只能由一个 capture controller 写入。
3. 采用 at-least-once 执行和幂等写入，不追求分布式 exactly-once。
4. 使用账号级水位线和有限重叠窗口替代周期性全历史翻页。
5. 网络调用、下载、文件 hash 和解析全部在数据库事务外执行。
6. 保留现有 raw response 和 immutable observation，历史结果通过 replay 修复，不重新付费抓取。
7. 所有业务使用方读取同一个带版本的 canonical projection。

### 2.3 非目标

- 不新增新的内容平台；微信视频号、快手继续保持既有人工或独立流程。
- 不重构内容理解、卖点提取、标签生成和媒体分析链路。
- 不启用游客网页抓取或绕过平台授权的方式作为生产来源。
- 不进行无预算、无冻结范围的历史全量重新抓取。
- 不将 TikHub 作为所有账号、所有字段、所有历史范围的默认全量来源。
- 不通过增加 SQLite 连接数或线程数解决运行问题。
- 不因抓取失败物理删除内容，也不将空值写成 0。
- 不把需求评审、测试通过、代码提交或进程重启当作生产改造完成。
- 不新增弹窗、提示框、预警文案、状态角标、Toast、红点、主动通知或新的告警页面。
- 不为展示抓取状态修改现有业务页面交互；来源、新鲜度和异常详情仅保留在后台追溯数据中。

## 3. 用户角色与核心场景

| 角色 | 核心诉求 | 必须支持的场景 |
| --- | --- | --- |
| 内容运营 | 尽快看到新视频和可信指标 | 继续使用现有列表和字段展示，不新增抓取状态提示 |
| 报告和数据使用方 | 同一截止点结果稳定可重放 | 日报、周报、CSV/Excel、SPU、卖点和标签使用相同 projection version |
| 值班和运维 | 快速发现和恢复故障 | 查询 backlog、provider health、DLQ、费用和任务链路 |
| 后端和数据工程 | 安全变更和验证 | raw replay、影子投影、迁移演练、故障注入和回滚 |
| 管理员 | 控制授权、范围和费用 | 管理名册、授权、provider 暂停、预算和历史补偿审批 |

核心业务场景包括：

1. 接受名册中的账号发布新视频，系统按固定周期发现并写入。
2. 已发现视频按照发布时间层级更新播放、点赞、评论、收藏和分享数。
3. Matrix 或官方源某账号断档，系统自动创建 TikHub 有界补偿任务。
4. 某账号 Token 失效或被限流，其他账号继续运行。
5. 视频变为私密、删除、地域限制、版权限制或恢复公开，历史事实不丢失。
6. worker 被杀死或 lease 过期后，任务自动重新领取。
7. 历史断档进入独立低优先级队列，不阻塞当天新视频。
8. provider 改变字段语义时，异常 observation 被隔离，不污染 canonical。
9. 值班人员通过后台日志和任务记录定位到账号、视频、run、attempt、slot 和 raw。

## 4. 统一术语和数据口径

### 4.1 身份口径

- 视频唯一身份：`platform + platform_content_id`
- 账号唯一身份：`platform + platform_account_id`
- URL 仅用于检索和辅助归一化，不替代平台内容 ID
- scope、run、slot、attempt、raw response、observation 均使用独立不可变 ID

### 4.2 时间口径

所有数据库时间统一保存为 UTC RFC3339 Z，调度、业务日和界面展示使用 `Asia/Shanghai`。必须明确区分：

| 时间 | 含义 | 规则 |
| --- | --- | --- |
| `published_at` | 平台视频发布时间 | 事件时间；保留 `published_at_raw` |
| `provider_data_at` | provider 明确声明的数据时间 | 接口没有时保持 NULL，不得伪造 |
| `request_started_at` | 请求发起时间 | 记录 attempt |
| `response_finished_at` | 完整收到响应时间 | 未封口 attempt 必须可监控 |
| `captured_at` | raw 固定完成时间 | 用于事实和截止点重放 |
| `recorded_at` | observation 写入数据库时间 | 用于识别 late arrival |
| `field_updated_at` | canonical 某字段最后成功更新时间 | 按字段保存，不使用一条复合时间代替 |
| `last_success_at` | 账号/内容/stage 最后完整成功时间 | 用于水位和 SLA |
| `next_attempt_at` | 下一次允许领取时间 | 用于退避和公平调度 |

所有业务窗口使用 UTC 半开区间 `[start, end)`。上海业务日必须显式转换，禁止混用无时区本地时间。

### 4.3 数值和字段状态

- 所有互动指标为非负整数。
- “真实为 0”“接口未返回”“字段不适用”“暂时失败”必须是不同状态。
- 平台可能进行数据清洗，计数下降不一定错误；系统必须保留事实、标记异常并进行确认。
- 单位转换只能发生在 adapter/解析层，并保留原始值和原始单位。
- canonical 新鲜度必须按字段计算。

统一字段状态：

- `fresh`
- `stale`
- `missing`
- `invalid`
- `not_applicable`
- `conflicted`
- `regression_suspected`

### 4.4 核心指标口径

- 最终抓取成功率：成功 item ÷ 到期 item。已确认的业务终态单独统计，不能静默删除。
- Attempt 成功率：成功 attempt ÷ 实际 attempt，只用于接口执行质量，不替代最终成功率。
- 视频完整率：冻结 scope 内已发现可用视频 ÷ 跨源 union 或平台金标应有视频集合。
- 发现延迟：首个可信内容 observation 的 `recorded_at - published_at`。
- 更新延迟：字段 `field_updated_at - next_due_at`；有 `provider_data_at` 时另计算真实平台数据延迟。
- canonical 重复率：多余 canonical 主键行 ÷ canonical 总行数。
- 字段准确率：满足金标容差的字段数 ÷ 可核对字段数。
- 积压年龄：当前时间减最早到期且未终结任务的 `next_attempt_at` 或 `next_due_at`。

## 5. 唯一目标架构

### 5.1 运行边界

1. `8766 API` 仅负责查询、轻量健康检查和接收业务命令，数据库连接启用只读模式。
2. 手工更新等写操作通过本机 Unix Domain Socket 发送给 capture controller。
3. Socket 权限固定为 `0600`，请求必须包含 `command_id` 和 `idempotency_key`。
4. Controller 是正式库唯一 writer，持有 writer lock、任务租约和运行版本收据。
5. API 只有在 controller 已持久化命令后才返回 `run_id`；controller 不可用时返回 503，不产生半任务。
6. Provider 网络 worker 可以并发运行，但所有正式库写入通过 controller 短事务提交。
7. Controller 崩溃不影响查询 API；API 崩溃不影响调度、heartbeat 和失败恢复。

### 5.2 数据流

```text
Planner 冻结 roster、窗口、来源策略
  ↓
父 Run 创建账号级 Child 后立即退出
  ↓
Worker 按 lease 领取账号/内容任务
  ↓
事务外调用 Provider
  ↓
Raw 临时文件 → fsync → 原子 rename → SHA-256
  ↓
Controller 短事务登记 attempt/raw/observation/checkpoint
  ↓
字段级权威路由生成 projection version
  ↓
API / 报表 / 导出 / SPU / 卖点与标签统一读取
```

### 5.3 数据源职责

| 平台/能力 | 主路由 | 降级与对账 | 禁止行为 |
| --- | --- | --- | --- |
| 抖音视频发现 | 通过 capability test 的 OpenAPI 账号优先官方；其他账号 Matrix 每 30 分钟 | 健康账号每日一次 TikHub 有界对账；主源失败立即触发，之后每 60 分钟补偿 | 未验权 OpenAPI 不计入 SLA；禁止网页游客抓取 |
| 小红书视频发现 | Matrix 每 30 分钟 | 健康账号每日一次 TikHub 对账；Matrix 失败后每 60 分钟补偿 | 页面打不开不得判断为内容不存在 |
| 抖音指标 | Matrix 优先；TikHub 按 operation 补齐 | 熔断期间保留旧值并标 stale | 禁止跨语义 operation 按最新时间乱补 |
| 小红书指标 | Matrix 优先；TikHub note detail 补齐 | 失败进入 item retry/DLQ | `view_count` 为 N/A，不使用 0 |
| 历史补偿 | 独立低优先级队列 | 复用同一个 provider core | 不得保留第二套分页/重试实现 |

### 5.4 字段权威规则

| 字段 | 权威顺序 | 保护规则 |
| --- | --- | --- |
| identity / URL / published_at | 已验收官方字段 → Matrix → TikHub detail/user_posts | 只补空或由更高权威来源纠正；保留 detail observation |
| `view_count` | Matrix → TikHub video_statistics | 缺失、占位 0 和旧值不得覆盖；下降需确认 |
| `like_count` | Matrix → TikHub video_statistics | detail/user_posts 只参与对账 |
| `comment_count` | Matrix → TikHub detail/user_posts | 允许平台审核导致的下降，但必须二次确认 |
| `collect_count` | Matrix → TikHub detail/user_posts | null 不得默认 0，按平台判断适用性 |
| `share_count` | Matrix → TikHub detail/user_posts | TikHub video_statistics 永久不进入 canonical，除非未来完成独立金标重新认证 |

新 operation 在完成字段合同和金标认证前默认 fail closed，只保存 raw/observation，不进入 canonical。

## 6. 功能需求

### FR-001 运行版本收据（P0）

Controller 启动时必须生成不可变运行收据，至少包含：

- 审批 commit SHA
- 实际运行 commit SHA
- config hash
- routing policy version
- schema/user_version
- 正式数据库绝对路径、inode 和 fingerprint
- PID 和启动时间
- 工作树状态
- scheduler job 清单
- 迁移、测试、影子和回滚收据

验收：运行 commit 必须等于审批 commit；目标构建不得来自脏工作树；缺失任一收据禁止切换生产。

### FR-002 账号范围冻结（P0）

- 每轮开始固化 roster version、平台、账号集合、来源策略和 UTC 半开窗口。
- 执行过程中的名册变化不得改变本轮完成率分母。
- 历史范围和当前业务日范围必须分开。
- scope unknown 不得被排除后宣称任务完整。

验收：计划账号数与 child 数守恒，任一任务可以恢复“计划抓谁、哪个窗口、使用什么来源”。

### FR-003 父轮次轻量化（P0）

- 父任务只负责冻结 scope、创建账号级 child、保存 child IDs 和计划总数。
- 父任务创建完成后立即退出，不直接执行账号网络循环。
- 父任务进度由 child 状态聚合得到。

验收：325 个账号 child 在 60 秒内创建完毕；父 checkpoint 在任意重启后可恢复。

### FR-004 账号级增量水位线（P0）

- 每个 `platform + account + provider + operation` 维护独立水位线。
- 业务水位由 `(published_at, platform_content_id)` 组成。
- Provider cursor 只属于当前 frozen run，不替代业务水位。
- 只有任务完整成功且分页质量校验通过后才能推进水位线。
- partial、超时、解析失败、cursor 异常不得推进。

验收：同一范围重复执行结果一致；错误分页不会制造不可恢复的数据空洞。

### FR-005 48 小时重叠与幂等（P0）

- 每轮发现从高水位向前重叠 48 小时。
- 内容继续使用 `(platform, platform_content_id)` 幂等 upsert。
- 重复页面和重复 cursor 只能追加新的合法事实，不生成第二条 canonical 内容。

验收：断档和晚到视频可补；canonical 重复率为 0。

### FR-006 安全分页停止（P0）

满足以下任一条件才允许正常停止：

1. Provider 明确返回 `has_more=false`。
2. 连续两页所有内容都有有效发布时间，且整页最大发布时间严格早于低水位，同时页内和页间排序满足单调约束。

遇到以下情况不得推进水位：

- cursor 重复
- 页面顺序倒置
- 时间缺失
- disposition 数量不守恒
- Provider 错误返回无限 `has_more=true`

验收：正常运行不再无界翻账号历史；排序或 cursor 异常会被记录并进入补偿。

### FR-007 页级 Checkpoint 和公平让出（P0）

- 每页 raw、page hash、cursor、解析 disposition 和 checkpoint 必须关联。
- 每次 claim 最多处理 5 页，随后 yield 并继续同一 child。
- 页数边界只表示让出 worker，不表示任务完成，也不能推进水位。
- 已经固定且 hash 通过的 raw 优先 replay，不重新购买。

验收：慢账号不会长期占用 worker；重启从最后完成页继续。

### FR-008 四维字段权威路由（P0）

- 使用 `platform + provider + operation + field` 决定 observation 是否有资格进入 canonical。
- 未登记的新字段、新 operation 默认隔离。
- 缺失、invalid、placeholder、旧 captured_at 不得覆盖已有可信值。
- `TikHub video_statistics.share_count` 必须被排除。
- 每个字段在后台投影中记录 value、provider、operation、raw ID、captured_at、provider_data_at、recorded_at、freshness 和选择原因，不要求业务 API 或页面新增展示。

验收：路由单元测试命中率 100%；两个已知 share 反例修复；未认证 operation 进入 share canonical 的数量为 0。

### FR-009 冲突、下降和异常突增（P0）

- 跨 operation 差异大于 `max(10, 5%)` 时标记 `conflicted`。
- 计数下降时保留 observation，先标记 `regression_suspected`。
- 同一认证 operation 第二次确认或第二可信来源确认后，才允许更新 canonical。
- 禁止简单使用 `max(old, new)` 隐藏平台真实纠偏。
- 10 倍以上且绝对增量超过 1,000 的异常突增也必须二次确认。

验收：异常事实可查，业务投影不会被一次异常响应静默污染。

### FR-010 不可变 Raw Replay 和重投影（P0）

- 既有 raw response 和 observation 不得修改。
- 新字段路由通过新的 projection version 重放生成。
- 同一输入和 policy version 重放三次必须得到完全相同的结果 hash。
- 旧报告不得原地改写，修复结果生成新的 correction revision。
- 重投影优先使用既有 raw，不发起付费请求。

验收：七日 raw 全量 replay 确定；所有新旧差异都能解释到规则和 raw。

### FR-011 Lease、Heartbeat 和 Owner Fence（P0）

- worker claim 时写 owner token、worker ID、generation、leased_at 和 expires_at。
- heartbeat 每 30 秒更新一次。
- lease 默认 5 分钟。
- watchdog 每分钟扫描过期 lease。
- 所有 checkpoint、raw 登记和 finish 必须校验 owner token + generation。
- 旧 worker 恢复后不得覆盖新 owner 的结果。

验收：100 轮并发竞争测试中同时有效 owner 不超过 1，旧 owner 成功提交数为 0。

### FR-012 周期 Watchdog（P0）

- 每分钟回收过期 lease、stale slot 和未封口 attempt。
- 僵尸恢复不能依赖服务重启。
- 回收后任务进入 retryable 状态并设置 next attempt。

验收：kill worker 后 6 分钟内任务重新可领取，不丢任务、不重复 canonical、不重复付费。

### FR-013 错误分类和重试（P0）

- 优先遵守 `Retry-After`。
- 没有 Retry-After 时采用 full-jitter，上限依次为：1 秒、5 秒、30 秒、2 分钟、10 分钟。
- 同一逻辑任务累计最多 5 次，不因重启、换 worker 或跨日清零。
- 401/Token 失效只允许 single-flight refresh 一次。
- 429、5xx、明确“请重试”、连接超时和连接中断可重试。
- 400、404、410、422、权限未开通、无效账号和明确业务终态不可按网络错误重试。
- `billing_unknown` 默认不得立即重新购买，必须先对账或检查 raw。

验收：不存在固定周期无限重试、同步重试风暴和未知计费重复购买。

### FR-014 限流和熔断（P0）

初始限制固定为：

- TikHub：4 并发，8 QPS
- Matrix：2 并发，1 QPS
- Douyin OpenAPI：额度验收前 1 并发，1 QPS
- 同一账号：最多 1 个外部调用

熔断规则：

- 同一 `provider + operation` 连续 5 次可重试失败，或最近 20 次失败率超过 50%，打开熔断 5 分钟。
- Half-open 只放行一个探测请求。
- 探测失败后逐步打开 10、20、30 分钟。
- 单 operation 熔断不得阻塞其他平台、账号和 operation。

验收：故障注入时 QPS、并发、熔断范围和恢复行为完全符合规则。

### FR-015 DLQ（P0）

满足以下条件进入 DLQ：

- 达到最大 5 次
- raw integrity 错误
- schema drift
- 未知字段语义
- 需要人工授权或处理

要求：

- 原 fetch slot 维持既有终态 `terminal_failed`。
- 追加独立、不可变的 `fetch_dead_letters` 记录。
- 保留原 scope、attempt、错误分类、最后 raw、建议动作和审批记录。
- DLQ 不再被普通 scheduler 自动消费。
- 人工 replay 创建新补偿 slot 或 attempt，原记录不回写。

验收：持续失败项不再堵住普通队列，且任一 DLQ 项可被定位、关闭或审批重放。

### FR-016 公平队列和历史隔离（P0）

固定容量分配：

- 60%：新发现、0–7 天指标及其重试
- 30%：8–30 天指标和评论计划
- 10%：缺口修复、DLQ replay 和历史回填

规则：

- 高优先级有积压时，低优先级不得借用其份额。
- 某类为空时，容量可以临时借给其他队列。
- 同一优先级按最早 due 和账号轮转，禁止单账号垄断。
- 历史 631 个 pending scan 必须进入独立队列和独立预算。

验收：一个持续失败账号或历史任务不会让其他账号超过两个发现周期未调度。

### FR-017 分层更新（P0）

| 内容年龄 | 核心指标周期 | 目标 P95 更新延迟 |
| --- | --- | --- |
| 0–2 天 | 每 2 小时 | ≤2.5 小时 |
| 3–7 天 | 每 6 小时 | ≤7 小时 |
| 8–30 天 | 每 24 小时 | ≤26 小时 |
| 31–90 天 | 业务活跃内容每 7 天 | ≤8 天 |
| >90 天 | 按需、报告或受控历史任务 | 由任务合同定义 |

补充规则：

- `comment_count` 属于核心指标，按上述频率更新。
- 评论明细不参与全局周期刷新，只由分析/审核任务触发。
- 媒体、评论明细和内容分析为独立 stage；其失败不得回滚已经成功的发现和指标。

### FR-018 内容可见性生命周期（P0）

一等状态：

- `unknown`
- `public`
- `private`
- `deleted`
- `geo_restricted`
- `copyright_restricted`
- `unavailable`

规则：

- 成功公开响应追加 `public` observation。
- 一次列表缺失只进入 `suspected_unavailable`，不得直接判删除。
- 官方权威响应可直接确认业务状态。
- 第三方不可见必须经过受控重复确认后才能晋升终态。
- 超时、限流、鉴权失败和解析失败不得改变可见性。
- 后续公开证据可以恢复为 `public`。
- 内容、raw 和历史指标永不物理删除。

验收：私密、删除、地域限制、技术失败和恢复公开可以被准确区分。

### FR-019 内容详情历史（P1）

- title、body、content type、published_at、账号映射变化必须追加 detail observation。
- 每个 detail observation 关联 raw ID、captured_at 和 hash。
- `content_items` 只作为当前 projection，不再是唯一历史真相。
- 报告截止点能够使用当时存在的 detail 事实。

验收：任一详情覆盖都可追溯，旧报告不会因主表更新失去历史字段。

### FR-020 手工更新（P1）

- API 不直接同步调用 provider。
- API 通过权限为 0600 的 Unix socket 发送 `command_id + idempotency_key + actor + frozen parameters`。
- Controller 持久化后返回 `202 + run_id/slot_id`。
- 相同幂等键返回原 run，不重复购买。
- Controller 不可用时返回 503，不产生半任务。
- 手工更新同样受预算、缓存、raw replay、限流和字段路由约束。

### FR-021 预算控制（P0）

- Provider、operation、任务三级预算。
- 所有 billed attempt，包括失败但计费的请求，都必须计入。
- 85%：暂停历史、老视频和低价值评论任务。
- 100%：停止所有非关键付费任务。
- 新视频发现和关键失败补偿保留独立容量，但不得突破总硬上限。
- 可以 replay 既有 raw 时禁止再次付费。
- 价格配置必须包含验证日期和来源。

验收：provider ledger 与账单差异不超过 1%，预算耗尽后不存在越权请求。

### FR-022 统一业务投影（P0）

以下使用方必须读取相同 projection version：

- 内容列表和搜索
- Overview/统计 API
- 单视频手工更新结果
- 日报、周报和汇总报告
- CSV/Excel 导出
- SPU audience
- 卖点、标签和其他指标调用方

现有业务 API 字段保持兼容，字段值统一由同一 projection version 产生，不新增前端提示类字段。provider、operation、raw/observation reference、captured_at、field_updated_at、freshness、conflict reason 和 projection version 只通过后台追溯查询和报告收据提供。

验收：100 条业务回归样本在所有调用方的同一字段结果 100% 一致。

### FR-023 健康检查（P0）

- `/livez`：O(1)，只判断 API 事件循环，不访问数据库，P95 <100ms。
- `/readyz`：轻量 `SELECT 1`、controller heartbeat、loaded commit 和实时 backlog age，P95 <500ms。
- Deep quality：controller 每 30 分钟异步执行 raw hash、FK、roster/window coverage 和水位质量检查。
- 旧 `/api/v8/health` 保留一个发布周期，但改为读取缓存并标记 deprecated。
- `/api/v8/scheduler` 只读 controller 缓存，不同步运行 coverage。

验收：raw 规模增长或深度检查失败不影响 `/livez`；controller 不可用时 `/readyz` 能准确失败。

### FR-024 后台运维查询能力（P1）

支持按照以下维度查询：

- platform
- provider
- operation
- account
- content
- run
- attempt
- slot
- raw
- error class
- queue class
- projection version

后台只读查询必须能够返回 backlog、oldest age、source health、circuit state、费用、DLQ 和下次重试时间；不新增前端运维页面、推荐动作提示或主动通知。

允许运维执行：

- 暂停/恢复 provider 或 operation
- 审批单项或冻结 cohort 的 DLQ replay
- 暂停历史队列
- 查看但不直接修改水位线和任务终态

所有操作写不可变 operator receipt。

### FR-025 数据质量对账（P1）

系统每日计算：

- scope 账号守恒
- 分页 input/existing/inserted/quarantined/filtered 守恒
- cursor 重复和排序异常
- 内容 ID、账号、发布时间、URL 缺失
- canonical 重复
- raw 文件缺失/hash 不一致
- 未封口 attempt
- 指标负数、占位零、异常倒退和异常突增
- 字段来源冲突
- 完整率、成功率、重复率、字段准确率、新鲜度和费用

基本守恒式：

```text
planned = succeeded + retryable + terminal + running
```

差异必须为 0。质量异常只允许阻止/回滚 canonical，不修改原始 observation。

### FR-026 结构化日志和异常记录（P1）

每条任务和 provider 日志至少包含：

```text
job_id
parent_run_id
run_id
attempt_id
slot_id
platform
provider
operation
account_id
content_id
raw_id
error_class
error_code
retryable

amount

```

禁止记录 Token、API key、完整 Authorization header、完整 cursor 和敏感账号资料。

## 7. 状态机和异常处理

### 7.1 Fetch Slot 状态

```text
pending
  → running
      → succeeded
      → retryable_failed → pending（next_attempt_at 到期）
      → terminal_failed
      → interrupted → retryable_failed
```

第 5 次失败或需人工处理时：

```text
retryable_failed
  → terminal_failed
  + fetch_dead_letters(open)
```

人工 replay 创建新补偿 slot/attempt，原 slot 和 DLQ 记录保持不可变。

### 7.2 内容可见性状态

```text
unknown
  → public
  → suspected_unavailable
      → private
      → deleted
      → geo_restricted
      → copyright_restricted
      → unavailable

private/deleted/restricted/unavailable
  → public（后续权威证据恢复）
```

技术错误保持原可见性，不得将 timeout、429、auth failure 或 parse error 映射为 deleted。

### 7.3 错误分类

| 错误类 | 示例 | 自动动作 | 是否自动付费重试 |
| --- | --- | --- | --- |
| `auth_refreshable` | 401、10008、2190008 | 单账号刷新一次 | 允许一次 |
| `auth_reauthorize` | 10010、撤权 | 标记待授权并停止 | 禁止 |
| `rate_limited` | 429 | 遵守 Retry-After，降低 token bucket | 到期后允许 |
| `provider_transient` | 5xx、明确请重试 | full-jitter，计入熔断 | 预算允许时 |
| `transport_billing_unknown` | 响应中断且计费不明 | 先对账和检查 raw | 默认禁止 |
| `invalid_request` | 400、422、schema 参数错 | terminal + 记录开发异常 | 禁止 |
| `content_terminal` | private、deleted、410 | 写 availability observation | 禁止 |
| `raw_integrity` | hash/size/JSON 错 | 隔离 raw，进入 DLQ | 仅人工审批 |
| `budget_blocked` | 余额或日预算不足 | 按优先级暂停 | 禁止 |
| `database_busy` | SQLite busy/locked | 停止 claim，记录最高级别异常，不重复 provider | 禁止新请求 |
| `database_io` | SIGBUS、IO error | 停止 writer，保护数据库 | 禁止 |

## 10. API、业务页面兼容和后台运维要求

### 10.1 API

- `GET /livez`
- `GET /readyz`
- 旧 `/api/v8/health` 一期兼容并 deprecated
- 内容 API 保持现有业务字段兼容；字段级 provenance、时间、freshness 和 conflict 仅由后台追溯接口提供
- 手动更新返回 `202 + run_id`，不在请求线程调用 provider
- 任务 API 返回 planned/claimed/succeeded/retryable/terminal/DLQ/running
- Source health API 返回 provider/operation 成功率、延迟、熔断和预算
- DLQ API 支持查询和受控 replay

### 10.2 业务页面约束

- 现有页面布局、交互和字段展示保持不变。
- 不新增 `fresh / stale / conflicted / N/A / unavailable` 等状态提示。
- 不新增字段来源、抓取时间、数据年龄、projection version 等展示信息。
- 不新增弹窗、提示框、预警文案、状态角标、Toast、红点、运维入口或主动通知。
- 不可用、缺失和不适用在后台投影中不得被错误写成 0；现有页面只消费修正后的字段值。

### 10.3 报告与导出

- 冻结 cutoff 和 projection version
- 记录 source coverage 和数据质量摘要
- Late arrival 或字段修复生成新 report revision
- 历史文件不原地覆盖

## 11. 后台可观测性与异常判定

| 观测对象 | 必须指标 | 后台异常判定与自动动作 |
| --- | --- | --- |
| 运行进程 | commit、PID、start、heartbeat、RSS/CPU、restart/crash | writer 不可用>60s或15m内崩溃≥2次时记录异常并停止继续领取 |
| SQLite | 事务耗时、busy/locked、WAL、checkpoint、integrity | locked持续或出现SIGBUS时记录异常并停止writer |
| 队列 | planned/claimed/succeeded/retry/DLQ/running、oldest age、throughput | 超过2周期或15m无进展时记录积压并暂停低优先级任务 |
| Provider | QPS、并发、错误类、Retry-After、circuit、延迟 | 最近20次失败率>50%时自动熔断 |
| 账号/内容 | last success、run/attempt/slot/raw 链路 | 单账号两个发现周期无成功时记录异常状态 |
| 数据质量 | 完整率、freshness、重复、冲突、倒退、N/A、availability | 低于门槛时隔离异常投影并保留证据 |
| 费用 | billed、amount、remaining、cost/new、cost/fresh field | 达到85%暂停低优先级任务，达到100%停止非关键付费任务 |
| 深度审计 | raw missing/hash、manifest、FK/integrity | raw损坏或缺失时隔离并保留证据 |

深度检查必须异步执行并缓存；即使 SQLite 被锁，关键异常也必须写入独立原子 JSONL spool。该能力只用于后台追溯，不发送通知，也不新增任何前端提示。

## 16. 发布、回滚和完成定义

### 16.1 发布前置

1. 干净 commit、schema、config 和 route version 冻结。
2. 1.12GB 正式库副本迁移演练三次。
3. `integrity_check`、foreign key、schema exact match 和行数对账通过。
4. S0 单元、集成、故障注入、raw replay 和金标全部通过。
5. 旧 writer 停止，WAL/SHM 和锁状态稳定。
6. 备份、回滚路径和运行收据完整。

### 16.2 切换前隔离验证

- 新旧链路共享同一 provider 响应，不产生双倍付费。
- 新 projection 写隔离表/库或 shadow receipt，不覆盖正式 canonical。
- 使用自动化测试、最近七个完整业务日 raw replay、金标和故障注入对账任务量、完整率、延迟、字段差异、费用、页数、锁、lease 和积压。

### 16.3 Canary

固定顺序：

1. 10 个账号完成一个发现与更新周期并对账。
2. 50 个账号完成一个发现与更新周期并对账。
3. 两级均通过后，逐步切换其余 accepted roster 账号。

任一级失败不得继续放量。

### 16.4 自动回滚触发

任一条件满足即回滚：

- 任意 canonical 重复
- 任一已知 share 反例复发
- SQLite lock 5 分钟超过 3 次
- 任意 SIGBUS
- 发现 P95 连续两个窗口超过 2 小时
- 最终成功率低于 99%
- 水位线错误推进
- owner fence 失效或跨账号写入
- 重复付费率超过 0.1%
- 单新增视频成本超过基线 120%
- 运行 commit/config/schema 不一致

### 16.5 回滚动作

1. 停止 v2 planner 创建新任务。
2. 等待已发出的 provider 请求结束或 lease 到期。
3. 切回经过字段止损的安全 projection，不恢复已确认会写错 share 的版本。
4. 从最后完整水位向前重叠 48 小时恢复。
5. Schema 19 保留，不做破坏性降级。
6. Raw、observation、usage、attempt、DLQ、lease 和发布收据全部保留。

### 16.6 最终完成定义

只有同时满足以下条件，改造才算完成：

- 目标架构已经实际部署，API 和 controller 边界可证明。
- 运行 commit、config、schema 和 projection version 与发布收据一致。
- SQLite 并发、故障注入和受控小流量验证中无 lock 任务失败、无 SIGBUS、无 owner 冲突和僵尸任务。
- 视频发现、更新延迟、最终成功率、完整率、重复率、字段准确率、恢复时间和积压全部达标。
- TikHub 不再进行无水位线的全历史日扫。
- Share 等字段只来自已认证的 provider-operation 合同。
- 私密、删除、地域限制和技术失败能够被区分并审计。
- 任一任务可定位到账号、视频、run、attempt、slot、raw 和错误原因。
- 断点恢复不重复抓取、不重复计费、不错误推进水位线。
- 自动化测试、raw replay、金标、小流量验证、运行收据和回滚演练均形成可复核证据。

## 19. 大白话说明

先让系统不再“边抓边锁死”，再让每个字段明确“自己应该信哪个接口”。然后把全账号大任务拆成一个账号一个小任务，只从上次成功水位往后补，并向前重叠 48 小时避免漏数。每次最多处理 5 页就让出 worker，旧视频页连续两页都早于水位才停止。

失败任务按照错误类型退避，最多 5 次；再失败就进死信，不能继续堵住新视频。历史补抓使用独立低优先级队列和预算。所有 raw 都保留，新规则优先从旧 raw 重算，不重复花钱。

最后完成自动化测试、raw replay、金标核对和两级小流量验证，再逐步切换生产。业务页面保持现状，不增加弹窗、预警信息或其他提示；问题只通过后台日志、任务记录和数据质量结果追溯。
