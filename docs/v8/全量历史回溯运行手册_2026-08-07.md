# 全量历史回溯运行手册（2026-08-07）

## 1. 当前状态与授权边界

本手册是实现与验收合同。用户随后明确回复“认同你的判断，请你执行”，因此按推荐的“两层口径”推进：全历史库存/当前数据，以及最近 6 个月 V2/V3 正式证据。首次 paid discovery 采用保守硬上限 `$9`、追加段 `$0`；触顶后必须凭实际状态重新报价，不自动扩额。该授权不包含：

- 自动扩大上述 `$9` 付费预算；
- 排除无平台身份的启用账号；
- 物理删除本地临时/恢复资产；
- 自动豁免删除、私密、404 等终态内容。

截至 2026-08-07 的只读基线：正式库 schema 11，共 9,547 条内容；160 个启用账号具有 183 个可采集平台身份（抖音 158、小红书 25）。另有 10 个启用账号没有抖音/小红书身份，默认会硬停，不会悄悄排除。从原两周任务重建的终页看，至少 163/183 个身份尚未证明历史已到底。

原基线 `c2c7eb0` 曾把 `_to_delete/` 和超过 100 MiB 的临时资产纳入跟踪。hygiene 提交 `2dd8135` 已仅解除 Git 跟踪并加入 ignore；60 个物理文件、439 MiB 数据及前后聚合 SHA-256 均保留。生产快照仍必须满足 `_to_delete=0`、跟踪文件 `>100 MiB=0`，不得 reset 或物理删除这些本地资产。

## 2. “回溯”的真实边界

现在抓回老作品，可以得到：

- 历史内容清单及平台身份；
- 抓取当时接口可得的累计互动指标；抖音可补播放，小红书当前详情接口返回的曝光长期为 0/NULL，不能承诺恢复可靠曝光；
- 抓取当时供应商仍可见的一级评论（每条内容上限 1,000 条）；
- 有媒体源且证据达 V2/V3 的重新评估；
- 基于当前 90 天行为证据窗的受众分类快照。

只依靠今天的平台接口，不能还原过去每一天当时的播放、点赞和评论时序。所有新快照都必须标记实际采集时间，不得倒写成历史日期。运行器因此将：

- `--end` 解释为“内容发布时间上界”；
- discovery 的快照时间单独锁定为 `discovery_snapshot_at`；
- 付费指标/评论的快照时间单独锁定为 `data_snapshot_at`；
- 证据完成后的受众分类再单独锁定 `classification_snapshot_end`。

`data_snapshot_at` 在报价闸通过、下游首次开跑时才冻结；仅报价后隔天再审批，重跑会刷新候选截面。任何下游阶段已经开始后，该截面不可再改，避免把今天抓到的累计值写进旧日窗口。

`--end` 不得晚于实际执行时间。

## 3. 两层口径

推荐默认使用两层口径：

1. 全历史库存层：所有可发现内容入库，补接口可得的当前累计互动和供应商当前可见的有上限一级评论。小红书可靠曝光、已删除、私密、平台限制或供应商不可见的评论无法保证。
2. 正式证据层：例如只对最近 6 个月内容做媒体、V2/V3 评估和正式卖点报告。

`--archive-before` 是这两层的分界：

- 早于边界的内容保留 `history-archive`，只进库存/当前数据层；
- 边界之后的内容使用 `history-backfill`，只有媒体就绪且评估达 V2/V3 才清标。

如果要求“所有历史内容都做正式卖点证据”，应把 `--archive-before` 设到全历史起点。这会大幅增加媒体下载、处理时间和磁盘占用，必须另行明确确认。

## 4. 防重买与存量缺口

默认付费阶段全部带 `--history-only`，只购买本次新标记的 `history-*` 内容。全量发现会重新请求动态首页；这是证明新内容无缝的必要成本，不能用过时首页缓存替代。同一战役的后续页由固定 end/cursor 槽位幂等复用。

发现对已在库内容只更新身份字段，不用列表页空值/截断文本覆盖已有富文本，也不用列表页的 0/NULL 曝光覆盖已有指标槽。对新内容要求真实 detail 接口，不把列表页派生详情当成完整正文。

这也意味着：现有 9,547 条里已经存在的旧指标/0/NULL/评论缺口，不会被本次 history-only 战役悄悄重买。如果用户的“数据更新回溯”也包含这些存量缺口，必须先产出独立报价，再开一个单独授权的 existing-gap repair campaign。

## 5. 安全门

正式执行前和续跑时都必须通过：

- 4173/8765 无服务监听；
- 原子建立 `runtime/operator-freeze.lock`，然后再次检查端口；
- Git 工作树干净；
- 当前提交不包含 `_to_delete/` 和 >100 MiB 跟踪文件；
- campaign contract 锁定 Git commit、DB path/inode、schema、active release/taxonomy/matcher hash、启用账号身份清单；
- active release 必须是可成功物化 matcher 的 `evaluation-v8`，否则在任何付费发现前硬停；
- 缺平台身份的启用账号为 0，或有明确的 `--allow-enabled-without-identity` 排除授权；
- SQLite `.backup` 完成，备份 `quick_check=ok`、FK 违规为 0，并产出 SHA-256/业务表计数 manifest；
- 仅回收超过 10 分钟的 stale fetch/media `running` 槽；仍未超时的运行槽一律硬停，不强抢；
- 测试进程带 `DCAR_TEST_DENY_FORMAL_DB=1`，任何测试打开正式库都立即失败；
- TikHub 免费账户预检通过，日志不持久化精确余额；
- 发现和后续付费预算均显式给定。
- 若证据窗扩大到全历史，先按发现 cohort 抽样估算媒体/ASR/OCR 空间，并检查磁盘安全余量；当前 wrapper 尚未自动完成容量估算，不得跳过人工容量门。

战役中不得换代码、换正式库、切 active release、修改账号身份清单后继续沿用旧 state。任一锚点改变都必须结束旧战役并重新审批。任务 ID 由 `end + archive-before` 派生，不与另一个窗口共用付费账本。

## 6. 命令

只打印计划，不写库、不调供应商：

```bash
.venv/bin/python scripts/run_full_history_backfill.py \
  --dry-run \
  --end '<实际开跑时已到达的固定时间，含时区>' \
  --archive-before '<正式证据起点，含时区>' \
  --discovery-budget '<已批准的发现首段上限>' \
  --discovery-extension-budget '<已批准的发现追加上限，可为 0>' \
  --max-pages 400
```

dry-run 会打印每个已配置的发现 tranche 和总 discovery ceiling；只有追加上限大于 0 时才会出现第二段，不得隐藏已配置追加段。

只做付费发现、入库、分组和后续报价（这不是 dry-run）：

```bash
caffeinate -dims .venv/bin/python scripts/run_full_history_backfill.py \
  --execute --discover-only \
  --end '<固定时间>' \
  --archive-before '<证据起点>' \
  --discovery-budget '<批准额>' \
  --discovery-extension-budget '<批准追加额或 0>' \
  --max-pages 400
```

发现完成并审批 `runtime/full_history_backfill/quote.json` 后，才能在同一 `end/archive-before` 下加：

```bash
--auto-ceiling '<已批准的后续总上限>' --local-batches '<本轮证据批次数>'
```

未给 `--auto-ceiling` 时，运行器必须停在报价闸。该参数只是 downstream ceiling，不包含发现首段/追加段。`quote.json` 必须分别写出 discovery ceiling、downstream ceiling 和两者相加的 campaign total ceiling。未知评论数会同时报 1 页下界和 1,000 条采集上限对应的页数上界，自动预算使用上界。占位曝光修复预算也必须计入 downstream ceiling。

## 7. 完成性与续跑

每个平台身份只能以下列两种原因之一标记发现完成：

- `provider_exhausted`；
- `range_start_reached`。

`page_limit_reached`、`missing_next_cursor`、`cursor_repeated`、失败页或账号数不一致均为 `partial/blocked`，立即停止报价和后续阶段。如果只是页数上限，在保持同一 `end/archive-before/discovery_snapshot_at` 下提高 `--max-pages` 重跑；已成功的固定游标页会从槽位/原始响应幂等重放，不再计费。

进程中断后，运行器会在备份完成后把超过超时阈值的 `running` 槽 CAS 恢复为可重试状态，并把恢复结果写入 state；新鲜 `running` 槽会阻断续跑。若供应商已返回但本地还未持久化就发生硬崩，本地账本无法绝对证明该请求是否已计费，仍存在极小的二次请求边界，需以供应商账单核对。

每个 discovery task 会产出独立 `*.contents.json` manifest，记录精确 `content_id` 及首次/最新 upsert action。因此 `history-backfill` 成功清标后，仍可精确验收本次新增队列。

任何 content 阶段 `partial/blocked`、媒体未就绪、证据低于 V2、重复指纹失败或剩余 `history-backfill > 0` 都返回非 0。不得手工 SQL 清除 `history-backfill`。媒体不可恢复时，必须保留标记并进入明示的人工/终态决策。

全历史中可能出现“列表仍可见，但详情/评论已删除、私密或返回 404”的内容。运行器会保留发现 raw 和失败槽并硬停，不会把 `terminal_failed` 冒充成功；只有用户批准可审计的 unavailable 终态/范围例外后才可继续验收。目前 wrapper 不会自动豁免这类项，因此不承诺完全无人值守跑完。

## 8. 阶段顺序

1. 锁、代码/DB/账号/release 合同、SQLite 备份与校验。
2. 禁止正式 DB 的离线测试门。
3. 全量发现，对新内容分 `history-archive/history-backfill`。
4. history-only 报价，包含抖音指标、抖音真实详情、小红书详情、双平台评论和抖音占位曝光修复；小红书指标在同一次详情响应内零额外计费派生。
5. 指标/详情、占位曝光修复、评论。若小红书详情已成功但指标派生前中断，续跑必须免费重放成功 raw，禁止发起未报价的第二次详情调用。
6. `history-backfill` 媒体处理与 active release 评估；仅 V2/V3 清标。
7. 给所有缺失内容生成重复指纹，队列清空后全库 rebuild 一次，不做每条重复 rebuild。全库 rebuild 本身仍是 O(n²)：当前 10,284 个指纹约需比较 52,875,186 对，正式运行前必须在备份副本基准测试耗时/内存；这项性能风险尚未被算法性消除。
8. 证据完成后，按固定当前截面对所有内容用户重算 90 天证据窗分类。
9. 脚本生成 postflight 采集/证据验收。在 review gate 清零后，再独立新建 custom report task/revision；报告生成尚未包含在本 wrapper 内，不得沿用已固定 content snapshot 的旧 report task。

## 9. 报告与看板验收

“采集与当前快照完成”不等于“正式报告完成”。

- `history-archive` 永久不做媒体/V2V3 评估，用全历史内容直接生成卖点报告会因 evaluation/media coverage 不足而 `partial`。
- 应分开产出“全历史库存/当前互动采集审计”与“证据窗内 V2/V3 正式业务报告”。
- 新增内容不会自动进入已经有 `task_contents` 快照的旧报告任务，必须新建 custom task。
- 全局 gray/conflict review gate 清零前，正式报告仍可能被阻断。
- 当前内容页仍固定只取第 1 页 50 条，API/CSV/UI 也未展示 `source_group`。在补齐分页/标记展示前，全量验收必须以 campaign manifest 和专用审计导出为准，不能宣称看板已可见全量。

## 10. 回滚

回滚前必须停止服务/调度并建立 operator lock。不得对带 WAL 的正式库做裸文件覆盖。使用备份 manifest 校验 SHA-256、`quick_check`、FK 和关键表计数，先恢复到新路径并用 `DCAR_V8_DB` 验证，再进行受控切换。

本战役会新增 raw responses、comment manifests、media/evidence 文件和 campaign manifests。DB 回滚后这些可成为孤儿资产，但不得根据模糊目录批量删除；只能依据本次 manifest 和 DB 引用差集做可审计清理。
