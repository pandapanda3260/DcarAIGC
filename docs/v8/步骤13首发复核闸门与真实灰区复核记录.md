## 本步修改

- schema 升级到 v5；`report_revisions` 增加 `invalidated_at` 与 `invalidation_reason`，历史报告不删除、不覆盖。
- 日报、周报和自定义报告统一增加首发硬闸门：首份有效 v8.1 revision 生成前，只要仍存在 `evaluation_gray_zone` 的 `pending`、`manual_required` 或 `in_review` 队列，报告任务立即失败、写入 `review_gate_blocked` 事件且不创建 revision。首发完成后，新灰区按正常口径进入报告的 pending 统计，不会阻断所有后续定时报表。

- 增加报告闸门、历史 revision 失效、清空卖点以及闸门放行后的 API 回归测试。

## 本步发现的问题与修复

- API 自定义报告测试原本故意保留待复核 fixture，启用全局闸门后正确返回 409。测试改为先通过正式人工复核接口解决 fixture，再断言闸门放行与报告生成；没有绕过闸门或降低断言。
- 人工取消卖点时旧 `matches` 会被自动匹配结果带入新版本。已在 `override` 分支显式按人工结论重建 matches，并增加无卖点回归断言。
- 运行时报告合同与新产物均已是 v8.1，但 `pyproject.toml` 的交付元数据仍声明 v8.0。已同步为 v8.1，并增加元数据与运行时常量严格相等的合同测试。
- 首发闸门最初会阻断未来任何灰区，且再次初始化可能把已有有效 v8.1 revision 的任务误标失败。已将闸门限定为“首份有效 v8.1 revision 前”，并要求数据库升级只降级没有任何有效 revision 的任务。新增回归覆盖首发后 pending 仍进入报告，以及重启不破坏有效任务状态。
- 扩展回归首次运行有 1 个失败：测试把低覆盖 fixture 的合法 `partial` 状态硬编码为 `succeeded`。断言已改为严格比较再次初始化前后的原状态；生产合同和覆盖率阈值未修改，重跑 46 项全部通过。
