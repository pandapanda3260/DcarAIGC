## 3. 六条不可触碰的不变量

每一条后面写了"碰了会怎样"。这些是拆除过程中真实踩过或差点踩到的坑。

### 3.1 `manual_evidence_sha256` 必须保留为恒 `None` 的键

`evaluation.py:169`：

```python
# v16 起系统无人工复核域：人工证据不再存在。哈希公式保留该键并恒为
# None——evaluation-v9 本就排除人工证据，既有 evidence_sha256 因此
# 逐字不变，不会触发全库"证据变化"重评。
"manual_evidence_sha256": None,
```

**碰了会怎样**：`evidence_sha256 = sha256_json(components)`。删掉这个键会改变 components 的规范化 JSON，导致**全库 31,737 条证据信封哈希漂移 → 系统判定"证据变化" → 5.9 万条评估全部重跑**。`evidence_envelopes` 表的同名列也一并保留（写入常量 `None`），不要"顺手清理"。

### 3.2 `_LEGACY_V15_TABLE_SQL` / `_LEGACY_V15_INDEX_SQL` 必须保留

`storage.py:1246`。v8→v9 迁移阶梯要在**当年的结构**上建表，不能用今天的 `SCHEMA_SQL` 模板。`_migrate_v8_to_v9` 会分支判断（第 1716 行）。

**碰了会怎样**：任何从 v8 或更早版本升上来的库（包括测试 fixture）在 v9 步骤就崩，且错误信息指向的是 v9 而不是这里，非常难查。

### 3.3 表重建期间必须 `PRAGMA legacy_alter_table=ON`

`storage.py:3496`，重建完成后在 `finally` 里关闭（3553/3556）。

**碰了会怎样**：SQLite 默认会在 `ALTER TABLE ... RENAME` 时**改写其它表里存储的 DDL 中的外键目标**。`evaluation_versions` 一改名，所有引用它的表的 `sqlite_master.sql` 都被重写，随后的字面量 DDL 比对（fail-closed 兼容性校验）全部失败。

### 3.4 表重建顺序：改名旧表 → 按模板建新表 → 显式列名拷贝 → 删旧表 → 重建索引

**碰了会怎样**（v15 迁移时的实测教训）：如果反过来"先建新表再 RENAME 成正式名"，`sqlite_master` 会把表名加上引号存储，字面量 DDL 校验直接失败。拷贝时必须显式写出 `id` 列，否则 rowid 重排。

### 3.5 DSL 阈值键名 `review_min` 不能改名

`evaluation.py:729-731` 有注释说明。它属于**已发布的规则合同**，参与 `matcher_rule_sha256` 计算。

**碰了会怎样**：改名 → 规则哈希变化 → release 运行时加载时的物化哈希校验失败 → 现有 release 直接不可用。名字里有 "review" 但和人工复核域无关，纯属历史命名。

### 3.6 灰区语义现在从存量字段推导，不再有 `pending_review` 列

`evaluation_selectors.py:221` 有 docstring 说明。判据是 `evaluation_source != 'manual_review'` 且 `60 <= selling_point_score < 75`。

**碰了会怎样**：改动这个推导等于悄悄改变历史 release 的正式入选口径。

## 5. 我发现但**没有修**的一个真缺陷（v8.7 合同升级引入）

`src/dcar_eval/v8/release_management_v9.py`（grep `^REPORT_VERSION`）：

```python
REPORT_VERSION = "dcar-content-operations-report-v8.6"
```

它只在 `_report_revision_count()` 里用，按 `contract_version = 'v8.6'` 统计 `report_revisions` 行数，是三处安全守卫的判据（按报错文案 grep）：

- `activate()` 前置检查：`"v8.6 report revisions already exist"`
- `_require_protected()`：`"v8.6 report revision boundary has been crossed"`
- **`rollback()`：`"v8.6 report revisions exist; rollback is forbidden"`**

**问题**：合同升到 v8.7 后，新报告写入的 `contract_version` 是 v8.7，这个计数**不再增长**。`rollback()` 里的那道守卫因此失明——即使 v8.7 报告已经发布出去，`rollback()` 仍会认为"没有已发布报告，可以回滚"。

**为什么我没改**：evaluation-v9 已经是线上 active release，`activate()` 不会再跑；改这个常量会改变三处守卫的语义边界，属于需要单独评审的发布域变更，不该混在拆除批次里。

**建议的修法**（供 Codex 评估，不是指令）：把单值常量改成集合 `{v8.6, v8.7}`（含未来版本），或直接改为"统计所有 `contract_version` 属于 v9 规则版本的修订"。这是**独立任务**，别和 Gate 0 提交混在一起。

> Codex 那份文档第 9 节列了 publisher 链三处 v8.6 漂移（`deploy/macos/publish_snapshot.py`、`deploy/server/install_snapshot.py`、`scripts/build_server_snapshot.py` 的 `EXPECTED_REPORT_VERSION`）。**这是第四处，而且它不在停用的 publisher 里，在活跃的发布守卫里。**
