# DCar Insight v8 运行与备份手册

## 当前运行边界

- 代码只支持 SQLite schema v19 / `dual-acquisition-profile-roster-v1`；当前报告合同为 `config/report_contract_v8_9.json`，v8.8 及更早合同只验证历史只读报告。
- 正式库不是 v19 时不得通过 API 启动顺带迁移。当前升级入口是精确封版18→19；17→18仅为历史兼容，本文后部的 v15→v16 流程只保留作历史恢复资料，不是当前上线入口。
- `runtime/operator-freeze.lock` 存在时，正式 API/writer 必须拒绝启动。它是离线迁移和切换的必备门，不是可跳过的普通配置。
- 正常模式的 4173 本地操作台固定连接 macOS 指定 writer 的 8766；8766 是唯一正式 API 和 scheduler。8765 只允许在 operator freeze 期间提供只读快照。
- snapshot publisher 是独立的无人值守 LaunchAgent：09:00 后每小时检查完整日链路，同日成功一次后幂等跳过；它不持有供应商密钥，也不运行 scheduler。

## 环境与安装

- macOS Apple Silicon。
- Python 由 uv 管理并锁定为 3.12.13；系统 Python 3.9.6 不承载产品依赖。
- Node 运行时由 npm 命令固定为 22.13.1。

首次安装：

```bash
python3 -m uv sync --frozen
npm --prefix app/web ci
```

Python 依赖以 `pyproject.toml` 和 `uv.lock` 为准；前端依赖以 `app/web/package.json` 和 `app/web/package-lock.json` 为准。锁文件不一致必须先修复，启动脚本不得隐式改锁。

## 4173 本地操作台启停

```bash
scripts/start_web_mvp.sh
```

- Web 入口：`http://127.0.0.1:4173`。内部 Web 为 4174，正式 API 为既有 8766 writer。
- 退出：在启动终端按 `Ctrl-C`；脚本只停止自己创建的 Web 子进程，不停止或重启 8766。
- `scripts/start_web_mvp.sh` 要求 `DCAR_SCHEDULER_ENABLED=0`、`DCAR_STARTUP_CATCHUP_ENABLED=0` 且 `DCAR_DAILY_CAPTURE_RECONCILE_FROM` 为空。任一条不满足都以 exit 78 拒绝启动。
- Web 默认先构建再以 production 模式运行，避免开发态即时编译和 HMR 影响日常页面加载；仅前端开发时显式设置 `DCAR_WEB_MODE=dev`。
- 不得把调度开关传给该脚本；这不是启动 writer 的入口。
- API 只监听回环地址，不应直接暴露到局域网或公网。手机号搜索使用 POST body；服务日志只记录 URL path。
- 登录账号存放在 `runtime/auth/sessions.sqlite3`（网关的 SQLite 账号库），验证码与找回票据的摘要用 `runtime/auth/pepper` 加密，两者都不入库不入 Git。脚本首次启动会把旧的 `runtime/auth/users.htpasswd` 一次性导入；之后新账号在登录页用准入名单内的手机号注册。本地默认 `DCAR_AUTH_SMS_PROVIDER=log`，验证码打印在启动终端 / `local-ui.log`（手机号脱敏）；要走真实短信需设置 `DCAR_AUTH_SMS_PROVIDER=tencent` 并提供 `runtime/auth/sms-tencent`（`dcar.env.local` 的 `TENCENT_SMS_*` 一节）。
- 账号管理由管理员/超级管理员访问 `/users` 页面；首个超级管理员、零超管恢复及离线操作使用 CLI：`PYTHONPATH=src/dcar_eval python3 -m uv run --frozen python -m dcar_auth.admin --db runtime/auth/sessions.sqlite3 <子命令>`，子命令含 `migrate / set-role / delete-user / changes / allow-phone / set-phone / set-password / disable-user / enable-user / revoke-sessions / revoke-challenges / list / import-htpasswd / export-htpasswd / sms-test`。
- 只有显式 `migrate` 会迁移/建库，普通账号命令遇到旧 schema 或缺失库会拒绝并提示先迁移，`sms-test` 则完全不打开账号库。服务器先验证真实短信收件，再由 release helper 完成正式迁移；只在 `deploy` 成功后绑定 `dcar` 手机号和登记准入名单，不能用手工 CLI 提前迁移线上旧库。

正常模式启动前会检查 8766 health 与 scheduler 合同：`mode=local_v8`、`read_only=false`、正式数据库名和 schema 兼容，同时 `requested/enabled`、`writer_lock.held`、`pipeline_reconcile.enabled`、`report_runtime.ready` 均为真；真实注册表必须包含 `pipeline_reconcile` 且不含 `history_recovery`，补偿模式必须是 `current_day_only`、间隔 3600 秒、付费轮次截止 20:00。8766 不可达或任一条件不满足时 exit 78，绝不回退 8765。残留 8765 只有被验证为 `read_only_replica` 时才警告后继续；可写或身份不明时 exit 78，正常验收仍要求最终停止 8765。

停止使用 `screen -S dcar-live-ui -X quit`。Mac 重启并登录后需要重新执行该命令；旧的 `dcar-view-ui` 与 `dcar-read-api` 不得继续运行。

4173 是本机可信操作台。页面上明确点击的新增、编辑、数据更新、媒体刷新和生成报告都会直接作用于正式库；TikHub 全部付费调用共享北京时间日总额 USD 100，默认任务上限也是 USD 100。单纯打开或强制刷新 `/selling-points` 不写业务数据，也不调用供应商。`/spu-audience` 页面可能按既有产品合同自动补算 stale 关联，不应用作无写入验收页。

operator freeze lock 存在时，不要为了看页面而删除锁。只能在已经运行的、明确为只读副本的 8765 上使用 `DCAR_REUSE_EXISTING_READ_ONLY_API=1`；脚本会校验 health 身份。

进入 freeze viewer 前必须先创建 freeze lock、停止 `dcar-live-ui` 和 8766，并确认正式 DB/WAL/SHM 无 holder。每次都用已受测的 `scripts/build_server_snapshot.py` 从正式库生成新的时间戳快照，不得复用 2026-08-20 的旧 viewer，也不得覆盖正在运行的 immutable 快照：

```bash
viewer_root="$HOME/Library/Application Support/DcarAIGC/viewer"
viewer_bundle="$viewer_root/$(date -u +%Y%m%dT%H%M%SZ)"
data_root="$HOME/Library/Application Support/DcarAIGC/data"
mkdir -p "$viewer_root/archive"

.venv/bin/python scripts/build_server_snapshot.py \
  --project-root "$PWD" \
  --db "$data_root/dcar_insight.sqlite3" \
  --legacy-db "$data_root/web_mvp.sqlite3" \
  --expected-user-version 19 \
  --output "$viewer_bundle"
chmod 0400 "$viewer_bundle/databases/"*.sqlite3
```

随后以 `DCAR_READ_ONLY=1`、scheduler/catch-up 关闭、`DCAR_V8_DB=$viewer_bundle/databases/dcar_insight.sqlite3` 启动独立 `dcar-freeze-viewer` SCREEN，再以 freeze lock 加 `DCAR_REUSE_EXISTING_READ_ONLY_API=1` 启动 `dcar-freeze-ui`。旧单文件 viewer 只移入 `viewer/archive/`，不删除。解除 freeze 时先停止这两个 SCREEN，再按 writer 手册恢复 8766 和 `dcar-live-ui`。

## 8766 writer 与自动调度

writer 只能按 [`deploy/macos/README.md`](../../deploy/macos/README.md) 渲染并人工加载 disabled-by-default LaunchAgent。`DCAR_DAILY_CAPTURE_RECONCILE_FROM` 是严格的 `YYYY-MM-DD` 日期，只能由 plist 传入，不得写进白名单解析的 `writer.env`。

时区固定为 `Asia/Shanghai`。scheduler 注册两个 profile 的 cron 并集，但每个计划槽都按 `activation_at(planned_at)` 门控：`matrix_hybrid_v1` 在 02:00/06:00/12:00/18:00 跑 Matrix 账号指标、02:10 跑 Matrix 30 天作品、06:00/12:00/18:00 刷新作品；`tikhub_managed_v1` 在相同时点跑对应 TikHub 账号指标、作品扫描与刷新。两种 profile 都在 03:00 跑 TikHub 全员对账，并共享 06:10/07:00/08:35 指标补全、07:30 汇总、08:00 日报和周一 08:30 周报。`content_pipeline` 和 `comments_refresh` 每 5 分钟运行，`pipeline_reconcile` 与 `report_reconcile` 每小时运行且 writer 启动后立即检查。

只有自动/页面报告共用报告专用进程内 RLock；供应商抓取和内容任务不持有该锁。报告主体在只读事务中构建，冻结结果使用短写事务。所有通过 `storage.transaction()` 发起的进程内 SQLite 写事务另由一把独立 RLock 串行，只覆盖 `BEGIN IMMEDIATE` 到 commit/rollback；供应商调用、媒体处理、报告构建和整个 `dispatch()` 均不在该锁内，跨进程写入也不受其保护。父轮次有收尾恢复，子扫描和内容批次仍可能在进程异常后留下僵尸。全员 TikHub 对账实测超过 9 小时，禁止将锁扩大到整个 `dispatch()`，否则会阻塞内容、评论、Matrix 和报告。APScheduler worker 数固定为 20。

小时补偿先为每个 registration 选择北京时间当天已经到点的最后一个槽，再按计划时刻排序执行；单个 key 失败不阻断后续 key。20:00 起不再新建当天七类付费补偿轮次，但 20:00 前已经创建的当天 partial 仍可续跑。`resume_due_work()` 在两个入口统一按冻结业务日期过滤：TikHub 看 `window_end`，Matrix works 看 `overall_end_at`，Matrix accounts 只接受 `rank_date=昨天`；跨日、字段缺失或显式历史 catalog 均不续跑。

同一次小时补偿的各 key 共用该次 `reconcile_at`，因此各父 `pipeline_round:*` attempt 的 `started_at` 都代表同一补偿起点，不精确代表各自实际 claim 时刻；Matrix/TikHub 子扫描有自己的 claim 时间，验收耗时不得用父 attempt 的这些列直接相减。

`history_recovery` 不再注册，也不再由小时补偿播种；旧 catalog 和旧子扫描会保留在数据库中，不补、不删。自动 `content_pipeline`、`comments_refresh` 和指标队列一律排除 `history-backfill` 或发布超过 30 天的内容，不保留 20% 历史席位。运营上只允许在另行明确授权后由 `range_backfill` 处理历史内容。

报告首次生成 `partial` 也视为报告父轮次完成；重复报告只按同一 `job_id + scheduled_for` 的真实终态判断。08:00 之后补到的扫描不能进入当天 08:00 冻结输入，因此当天日报可能永久为可发布的 `partial`。供应商轮次不持有报告锁，所以自动日报不会再因供应商轮次占用报告锁而排队；它仍可能受其他自动/页面报告、APScheduler 线程池饱和、睡眠/misfire 或调度器延迟影响。数据库要到实际 claim 后才出现父轮次；验收看 writer 的 APScheduler 日志，或事后比较 `identity.scheduled_at=08:00` 与 `started_at`。

本地链路已把内容列入 `terminal_ids` 且所有失败阶段均显式 `retryable=false` 时，该内容按终态收口。冻结业务日已经过期的内容或评论批次必须在供应商/本地处理前把剩余项记为 `skipped/business_day_expired`，清空 pending 并释放 reserved；不得让一个不可重试条目永久占住每 5 分钟队列。

`startup_catchup` 和小时 `report_reconcile` 仍严格是 `report_only`：它们会补缺失的过去日报/周报，但不调用供应商。页面手工报告也使用同一报告专用锁，排队期间页面任务保持 queued。

父 `pipeline_round:*` 的 checkpoint/finish 遇到 SQLite busy/locked 后，会在最多 195 秒内做 6 次有界恢复；完成 checkpoint 但未 finish 的轮次下次只做收尾，不重跑业务。该保证不扩展到 Matrix/TikHub 子扫描、内容批次和 catalog，它们的陈旧 running 仍依赖 writer 重启时的既有恢复。

补偿日缺失早期多时点槽时，`required_closeout_rounds` 会拒绝预算 closeout；历史 catalog 的 pending 也会继续出现在 due inventory。当前各分类上限等于全局上限，不以 closeout 成功作为本次健康门。`daily_pipeline_summary` 即使延迟或由补偿器创建，子记录的 `identity.at` 和汇总 `captured_at` 仍固定为冻结的计划时刻 07:30；其中 `discovery_coverage` 按 07:30 cutoff 计算，不包含之后完成的扫描，不能作为全天最终完成度。

## TikHub 未知计费的人工对账

网络中断或进程被强制停止后，已经越过发送边界但无法证明供应商是否计费的请求会进入 `billing_unknown`。系统会冻结同一槽位的后续付费重试；充值和熔断恢复探针不会自动解除这类冻结。预算摘要中的 `billing_unknown.unresolved_count/unresolved_microusd` 是全量未结算敞口，`budget_day_count/budget_day_microusd` 是当天部分。这是日常核对项，不另建告警。

先用 WAL-aware 的只读模式分页导出。该命令不使用 `immutable=1`、不修改数据库，也不触发 TikHub 请求：

```bash
db="$HOME/Library/Application Support/DcarAIGC/data/dcar_insight.sqlite3"
PYTHONPATH=src/dcar_eval:. .venv/bin/python -m v8.billing_reconciliation \
  --db "$db" list --limit 100 --after-id 0
```

每条记录必须在 TikHub 后台逐条核对。清单会给出内容平台 ID/账号平台 UID、请求时间、端点，以及对本地 raw 做 byte size + SHA-256 校验后提取的 `detail.request_id`；优先用 TikHub request ID 精确匹配后台账单，缺少 request ID 时才组合端点、外部内容/账号 ID 和时间核对。`evidence_ref` 必须精确到唯一后台账单行，不得跨 usage 复用。`billed` 表示后台确认已计费，`unbilled` 表示后台确认未计费；无法唯一确认、清单 `valid=false` 或 `evidence_valid=false` 时保持原状，禁止猜测、批量默认、删除 usage 或用补偿行冲账。先做 dry-run，记录返回的 `fingerprint`：

```bash
PYTHONPATH=src/dcar_eval:. .venv/bin/python -m v8.billing_reconciliation \
  --db "$db" settle \
  --usage-id <usage_id> \
  --expected-slot-id <slot_id> \
  --expected-attempt-number <attempt_number> \
  --outcome billed \
  --evidence-ref '<TikHub后台非敏感账单证据编号>' \
  --operator-ref '<操作人标识>'
```

正式写入前必须在已安装 LaunchAgent 绑定的唯一 canonical checkout 创建 `runtime/operator-freeze.lock`（当前用户所有、普通非 symlink、单硬链接、权限精确 0600），停止 8766 writer、`dcar-live-ui` 和其他写库 CLI，并按本文“备份与发布”一节使用 SQLite online backup 生成项目外备份。CLI 会核对已安装 plist 的 checkout、正式库、freeze 路径，并独占 `$HOME/Library/Application Support/DcarAIGC/runtime/writer-worker.lock`；从其他 worktree 运行、writer 仍在、freeze 不合规、账本/批次漂移、槽位关联无效、身份或 fingerprint 变化、已有 raw 响应但 HTTP 状态未知或为 2xx 时全部失败式停止。fingerprint 同时绑定本次 `billed/unbilled` 决策、证据编号、操作人标识和实际 OS 用户，任何一项改变都必须重新 dry-run。确认 dry-run 没变化后才执行单条 apply：

```bash
PYTHONPATH=src/dcar_eval:. .venv/bin/python -m v8.billing_reconciliation \
  --db "$db" settle \
  --usage-id <usage_id> \
  --expected-slot-id <slot_id> \
  --expected-attempt-number <attempt_number> \
  --outcome billed \
  --evidence-ref '<TikHub后台非敏感账单证据编号>' \
  --operator-ref '<操作人标识>' \
  --expected-fingerprint '<dry-run返回值>' \
  --apply --confirm-tikhub-reviewed
```

确认未计费时必须先以 `--outcome unbilled` 重新 dry-run，再用它返回的新 fingerprint apply，不能复用 billed 的 fingerprint。已计费结算保留 usage 金额和 budget 计数；未计费结算将该 usage/attempt 置零，并对原 budget batch 精确减 1 次请求和原金额。两种情况都会保留原始错误和 raw 证据，并把填写的操作人标识、实际 OS uid/用户名写入不可更新、不可删除的 `scheduler_run_attempts` 操作回执。同一槽还有其他未结算 usage 时不会解冻；最后一条结算后才恢复该槽最新 attempt 的错误并允许正常队列按既有规则重试。它不会新建历史任务，也不得手工触发历史补抓。

apply 后立即重跑 `list`，确认总数只减少 1、金额按决策变化，并保存返回的 receipt run/attempt ID。结束全部单条操作后再解除 freeze、启动 writer，让自然调度续跑。provider circuit 若仍 open，仍需走原有授权 live probe；账单结算不会伪造探针成功。

writer 每次启动会把仍有任意 `billing_unknown` 的全部关联槽位（含当前 succeeded、以后可能因派生落库失败而重开的槽）同步为常数时间门禁，并写不可变同步回执；这只修复派生门禁，不修改 usage/attempt 金额，不抓取历史数据。

## 媒体生命周期任务的注册口径

`/api/v8/health.media_lifecycle.activation.mode` 是正式激活模式，`lifecycle_jobs_enabled` 只有在模式为 `active`、scheduler 已启动且 `media_archive`、`media_retention`、`media_restore` 三项都真实出现在注册表时才为 `true`。不能再用“全局 scheduler 已开启”冒充媒体生命周期已开启。

当前正式库仍是 `enrollment_only`，只有两个 canary，尚无 completion、consumer、archive/hot-release/restore 完整证明；因此调度器只有 16 个非媒体任务、上述三项未注册是正确的安全状态，不是漏装。现在不得直接切 `active`。必须先按部署手册完成两个固定 canary 的 completion 封存、真实消费者配对、归档和热原件释放、完整恢复及 durable run/attempt 证据，再追加 `active` 回执并重启 writer；旧媒体不补登记。

## 历史资料：正式库 v15→v16 离线 candidate 流程

以下只记录旧 v15→v16 恢复合同；当前 schema19 部署不得照此执行：

1. 保持 canonical operator freeze lock，停止 8765、8766、range/backfill 和其他直连 CLI。
2. 确认正式 DB/WAL/SHM 无业务进程持有，WAL 为空或不存在。
3. 若项目根仍在 `~/Documents`，必须先归档旧 writer/publisher plist，再在同一 APFS 卷上把唯一可写根原子移到 `/Users/mark/Projects/DcarAIGC`。禁止复制出第二份正式 DB 或保留两个可运行 checkout。移动后在新根运行 `python3 -m uv sync --frozen` 并重跑本节目标测试。
4. **项目根移动必须早于 `prepare-backup`**。backup receipt 会绑定正式 DB 的绝对路径，v16→v15 恢复入口也会复核该路径；回执生成后再迁根会使回滚合同失效。下面所有 `$PWD` 都必须是最终 canonical root。

### 服务器认证库备份与恢复

认证发布、回滚和恢复都有磁盘门：smoke 前/操作前检查一次，获取 `snapshot-install.lock` 后且停服前再检查一次。
工具按 DB、sidecar、备份、日志、receipt/旧 unit 和安装目标的实际文件系统累计临时写入预算，预算完成后仍须同时保留 2 GiB 与总容量 3%，
使用普通服务账号可用空间（排除 root 保留块）；receipt 保存两次测量。无 CLI/环境变量跳过开关。96% 使用率不能单独证明容量不足，
也不能用“再有几 GiB”忽略大型数据库的迁移/恢复副本；检查失败保持旧服务不动，先扩容或逐项确认可安全搬移的生成物，禁止自动删除历史数据。

服务器的账号库 `/var/lib/dcar-aigc/auth/sessions.sqlite3`（账号与角色、手机号绑定、准入名单、验证码、会话、删除墓碑）由 `dcar-auth-backup.timer` 每日 03:30 用 `/usr/local/libexec/dcar-auth-backup` 在线备份到 `/var/backups/dcar-aigc/auth`（root:root 0700）。去重、清理与 `--verify` 共用严格配对验证：文件名、manifest 结构/时间/名称、SHA-256、字节数、表计数、schema、quick_check、foreign_key_check、DELETE journal 全部相符才视为有效备份。保留 30 天，永不删除最新一组有效 DB + manifest；孤立或损坏文件保留诊断，不影响去重或有效备份保留。备份含密码哈希与手机号，不含 pepper（`/etc/dcar-aigc/credentials/auth-pepper`）。库固定 `journal_mode=DELETE`，既有 WAL 库不会被健康检查误判正常。

释放容量必须另行确认具体对象，不能删除审计记录来换取空间。

1. 停止 `dcar-auth`，停止本机及其他会话中的所有账号 CLI 写入；确认无后台脚本仍在写库。备份工具可只读保存，但不要在处置期间同时启动迁移/恢复。
2. 首先只读检查并留存完整原件；禁止先运行编辑器、`truncate`、`sed -i` 或删除任何中间行。下面的离线工具由 root 执行，检查服务确已 inactive/failed、取得数据库写事务和日志文件排他锁；修复前在新的备份目录保存完整原日志、原 mode/owner/SHA-256 和 JSON 回执并 fsync。原始日志含身份信息，备份目录须为 root:root 0700，证据文件 0600。
3. 只允许隔离最后一段“未换行且语法不完整”的残尾；完整且合法的最后一条 JSON 缺换行时只补换行，记录本身不丢弃。中间坏行、换行结尾的坏记录、结构完整但非法的事件均拒绝自动修复，保留原件并转人工证据核对，绝不能删掉坏行假装日志完整。

```bash
REL="$(readlink -f /var/www/dcar-aigc/current)"
sudo systemctl stop dcar-auth
# 先只读检查；此调用不修改日志或数据库。
sudo env PYTHONPATH="$REL/src/dcar_eval" "$REL/.venv/bin/python" \
  "$REL/deploy/server/libexec/dcar-auth-log-repair.py" \
  --db /var/lib/dcar-aigc/auth/sessions.sqlite3 \
  --change-log /var/lib/dcar-aigc/auth/auth-changes.log
# 仅在检查确认为允许处理的残尾时执行；完整原件和回执由 helper 先持久化保存。
sudo install -d -o root -g root -m 0700 /var/backups/dcar-aigc/auth-log-repair
sudo env PYTHONPATH="$REL/src/dcar_eval" "$REL/.venv/bin/python" \
  "$REL/deploy/server/libexec/dcar-auth-log-repair.py" \
  --db /var/lib/dcar-aigc/auth/sessions.sqlite3 \
  --change-log /var/lib/dcar-aigc/auth/auth-changes.log \
  --repair-tail --backup-dir /var/backups/dcar-aigc/auth-log-repair
# 修复退出码 3 是预期：有审计不确定性，保持停止，先完成人工对账。
sudo -u dcar-aigc env PYTHONPATH="$REL/src/dcar_eval" "$REL/.venv/bin/python" \
  -m dcar_auth.admin --db /var/lib/dcar-aigc/auth/sessions.sqlite3 changes
```

`changes` 通过只证明剩余日志结构可读；即使退出 0，也**不证明隔离的未知变更已经核实**。依据完整原件、修复回执和当前账号状态核对受影响时段；
缺少 commit 的 intent 按保守待核实处理。涉及未知密码、提权或启用的账号先线下核实身份，必要时先停用并重新设密；已确认的删除/降权/停用应补执行。
无法确定影响范围时按全体账号核查，不能仅因登录成功而结束。记录核对结论、保存新的已验证账号库备份后，才 `sudo systemctl start dcar-auth`，
验证健康、管理员身份和一项可控安全变更正常，并确认磁盘/日志没有继续报错。工具不自动重启服务。
