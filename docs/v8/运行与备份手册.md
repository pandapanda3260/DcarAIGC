# DCar Insight v8 运行与备份手册

## 当前运行边界

- 代码只支持 SQLite schema v16 / `remove-manual-review`；报告合同为 `config/report_contract_v8_7.json`。
- 正式库若仍为 v15 / `spu-llm-assist`，不得通过 API 启动顺带迁移。正式路径的 schema 不匹配会失败式停止，只有离线 v15→v16 candidate 流程可改变正式库。
- `runtime/operator-freeze.lock` 存在时，正式 API/writer 必须拒绝启动。它是离线迁移和切换的必备门，不是可跳过的普通配置。
- 8765 固定为无调度 UI/API；唯一 scheduler 只能在 macOS 指定 writer 的 8766 上运行。
- snapshot publisher 是独立的无人值守 LaunchAgent：09:00 后每小时检查完整日链路，同日成功一次后幂等跳过；它不持有供应商密钥，也不运行 scheduler。

## 环境与安装

- macOS Apple Silicon。
- Python 由 uv 管理并锁定为 3.12.13；系统 Python 3.9.6 不承载产品依赖。
- Node 运行时由 npm 命令固定为 22.13.1。

首次安装：

```bash
python3 -m uv sync --frozen
npm --prefix app/web ci
```

Python 依赖以 `pyproject.toml` 和 `uv.lock` 为准；前端依赖以 `app/web/package.json` 和 `app/web/package-lock.json` 为准。锁文件不一致必须先修复，启动脚本不得隐式改锁。

## 8765 UI/API 启停

```bash
scripts/start_web_mvp.sh
```

- Web 入口：`http://127.0.0.1:4173`。内部 Web 为 4174，API 为 8765。
- 退出：在启动终端按 `Ctrl-C`；脚本会停止自己创建的子进程。
- `scripts/start_web_mvp.sh` 要求 `DCAR_SCHEDULER_ENABLED=0`、`DCAR_STARTUP_CATCHUP_ENABLED=0` 且 `DCAR_DAILY_CAPTURE_RECONCILE_FROM` 为空。任一条不满足都以 exit 78 拒绝启动。
- 不得把调度开关传给该脚本；这不是启动 writer 的入口。
- API 只监听回环地址，不应直接暴露到局域网或公网。手机号搜索使用 POST body；服务日志只记录 URL path。

operator freeze lock 存在时，不要为了看页面而删除锁。只能在已经运行的、明确为只读副本的 8765 上使用 `DCAR_REUSE_EXISTING_READ_ONLY_API=1`；脚本会校验 health 身份。

## 8766 writer 与自动调度

writer 只能按 [`deploy/macos/README.md`](../../deploy/macos/README.md) 渲染并人工加载 disabled-by-default LaunchAgent。`DCAR_DAILY_CAPTURE_RECONCILE_FROM` 是严格的 `YYYY-MM-DD` 日期，只能由 plist 传入，不得写进白名单解析的 `writer.env`。

时区固定为 `Asia/Shanghai`：

- 每日 02:00：账号发现和内容抓取。
- 每日 02:20：下载待处理媒体。
- 每日 03:00：处理本地媒体证据。
- 每日 07:30：执行媒体截止、增量评估和重复指纹处理。
- 每日 08:00：生成昨日日报。
- 每周一 08:30：生成上一自然周周报。
- 每 1 小时：执行一次当天完整链路 reconcile，并独立检查遗漏的日报/周报；writer 启动后也立即检查。

小时 reconcile 与六个 Cron 共用同一个依赖顺序保障：`capture → download → processing → cutoff → daily report → 周一 weekly report`。它只补北京时间当天已到时且缺失的业务槽，不补历史 capture，也不产生独立 reconcile run。付费 capture 已有终态绝不重跑；仅进程中断的 capture 使用同一日 task ID 和原 USD 8 总上限自动续跑。无供应商调用的下游 `failed/interrupted` 槽按小时重试。

“02:00 精确槽”由业务槽算法保证，不要误解为回调必须在 `02:00:00` 到达。Cron 负责低延迟，小时 reconcile 负责进程重启或睡眠唤醒后的正确性；上游未终态时，下游不抢跑。publisher 只有在当天抓取、下载、处理、截止、日报及周一周报全部达到允许终态后才发布，未就绪会在构建和 SSH 前退出并于下一小时重试。

`startup_catchup` 和小时 `report_reconcile` 严格是 `report_only`：只可创建或重试到期的 `daily_report` / `weekly_report`，不运行 capture、media 或 cutoff，因此不会通过该路径产生供应商费用。

### daily capture 状态与质量门

- `succeeded`：所有最终待执行对象完成。
- `partial`：存在真实成功，也存在局部未解决项。`partial` 是终态，同一日槽包括 `operator_retry` 在内都不重跑。
- `failed`：全局鉴权/余额/预算阻断、没有任何有效成功，或顶层异常。`budget_blocked` 仍属于 `failed`；不得为了通过验收提高 USD 8 上限，小时 reconcile 不重跑该终态。
- `interrupted`：writer 进程在运行中退出。小时 reconcile 只对这个状态自动续跑同一日 capture，沿用同一 task ID 和剩余预算，不会取得第二份 USD 8；显式 `operator_retry` 仍用于人工诊断入口。
- `skipped`：没有 enabled 身份等无需执行情形。

运行状态和上线质量门是两件事：质量门不会篡改 scheduler run 状态。验收必须同时满足：

- `len(discovery) == monitored_accounts`，且 discovery `succeeded` 比例不低于 90%。
- `len(content_updates) == monitored_contents`，且 `succeeded + already_succeeded` 比例不低于 60%。
- `blocked_providers` 为空。`provider_usage` ledger 是权威账本：details 上报小计、ledger 和声明预算都必须是有限值，成本非负、预算为正；必须同时满足 `ledger >= details 上报小计`、`ledger <= 声明预算` 和 `ledger <= USD 8`。

details 小计会因已计费的失败或重试而少于 ledger；两者精确相等只是诊断字段，不参与 `quality_gate.passed` 判定。

`DAILY_CAPTURE_CONTENT_LIMIT=3000` 是当天从 eligible pool 中选出的 cohort 上限，不是全库覆盖量。60% 只衡量这批最多 3,000 条是否完成，不能解读为“全库覆盖率 60%”。

## 正式库 v15→v16 离线 candidate 流程

以下是唯一允许的正式 schema 变更路径：

1. 保持 canonical operator freeze lock，停止 8765、8766、range/backfill 和其他直连 CLI。
2. 确认正式 DB/WAL/SHM 无业务进程持有，WAL 为空或不存在。
3. 若项目根仍在 `~/Documents`，必须先归档旧 writer/publisher plist，再在同一 APFS 卷上把唯一可写根原子移到 `/Users/mark/Projects/DcarAIGC`。禁止复制出第二份正式 DB 或保留两个可运行 checkout。移动后在新根运行 `python3 -m uv sync --frozen` 并重跑本节目标测试。
4. **项目根移动必须早于 `prepare-backup`**。backup receipt 会绑定正式 DB 的绝对路径，v16→v15 恢复入口也会复核该路径；回执生成后再迁根会使回滚合同失效。下面所有 `$PWD` 都必须是最终 canonical root。
5. 在项目外创建当前用户独占的 migration-lock 目录，权限必须精确为 `0700`。只创建目录，不得手工创建或改写 lock 文件；脚本首次以 `O_EXCL` 写入固定 magic，后续阶段只接受 backup/migration receipt 绑定的同一 inode、`0600` 权限和精确内容：

```bash
install -d -m 700 /absolute/path/outside/project/v16-locks
```

首次 `prepare-backup` 要求 lock 路径不存在。若进程在生成 backup receipt 前异常退出，只能在核对父目录、固定 magic、inode、权限且确认无进程持锁后移除该孤儿 lock，再从 `prepare-backup` 重跑；不得覆盖或编辑。

6. 使用受测入口生成项目外 v15 备份。入口会调用 SQLite backup API、执行独立 scratch restore 验证、复核 SHA-256 / schema / `quick_check` / `integrity_check` / `foreign_key_check`，并以 O_EXCL 产生 `dcar-v16-offline-backup-v1` 回执；禁止手工拼写回执：

```bash
.venv/bin/python scripts/migrate_v8_schema.py prepare-backup --help

.venv/bin/python scripts/migrate_v8_schema.py prepare-backup \
  --source-db "$PWD/app/data/dcar_insight.sqlite3" \
  --backup /absolute/path/outside/project/dcar_insight_v15_backup.sqlite3 \
  --expected-source-sha256 <formal-v15-sha256> \
  --from 15 \
  --freeze-lock "$PWD/runtime/operator-freeze.lock" \
  --migration-lock /absolute/path/outside/project/v16-locks/dcar-v16-migration.lock \
  --receipt /absolute/path/outside/project/v15-backup-receipt.json
```

7. 先用当前脚本的 `--help` 核对参数，再生成项目外、与正式库同文件系统的 v16 candidate：

```bash
.venv/bin/python scripts/migrate_v8_schema.py build-candidate --help

.venv/bin/python scripts/migrate_v8_schema.py build-candidate \
  --source-db "$PWD/app/data/dcar_insight.sqlite3" \
  --candidate /absolute/path/outside/project/dcar_insight_v16_candidate.sqlite3 \
  --expected-source-sha256 <formal-v15-sha256> \
  --from 15 \
  --to 16 \
  --freeze-lock "$PWD/runtime/operator-freeze.lock" \
  --migration-lock /absolute/path/outside/project/v16-locks/dcar-v16-migration.lock \
  --backup-receipt /absolute/path/outside/project/v15-backup-receipt.json \
  --receipt /absolute/path/outside/project/v16-migration-receipt.json
```

8. 核对 candidate 的 v15→v16 lineage、精确 schema-object delta、数据投影、manifest、`user_version=16`、完整性与 migration receipt，再使用 `scripts/install_writer_database_candidate.py` 执行 migration-receipt 驱动的原子安装。安装器会重新校验冻结的 v15 源、v16 candidate、回执与 SHA，保留切换前 DB/sidecar，任一故障都原子恢复。不得手工覆盖 DB。

```bash
.venv/bin/python scripts/install_writer_database_candidate.py --help

.venv/bin/python scripts/install_writer_database_candidate.py \
  --formal-db "$PWD/app/data/dcar_insight.sqlite3" \
  --candidate /absolute/path/outside/project/dcar_insight_v16_candidate.sqlite3 \
  --migration-receipt /absolute/path/outside/project/v16-migration-receipt.json \
  --expected-migration-receipt-sha256 <migration-receipt-sha256> \
  --backup-dir "$PWD/app/data/backups/v15-before-v16-YYYYMMDD-HHMMSS" \
  --receipt /absolute/path/outside/project/v16-install-receipt.json \
  --freeze-lock "$PWD/runtime/operator-freeze.lock"
```

`--backup-dir` 必须是 `app/data/backups/` 下尚未存在的直接子目录，candidate、migration receipt 与 install receipt 都必须位于项目根之外且不可覆盖。执行前仍必须以当前 `--help` 和目标故障注入测试为准，不得复用旧 v11 参数。

正式切换前，`tests.test_restore_writer_database_backup` 的全部 reverse-restore checkpoint 故障注入必须通过；它证明任一 durable transition 失败都恢复字节相同的原 v16。真正需要 schema 回退时，只允许使用 receipt 驱动的原子恢复入口：

```bash
.venv/bin/python scripts/restore_writer_database_backup.py --help

.venv/bin/python scripts/restore_writer_database_backup.py \
  --formal-db "$PWD/app/data/dcar_insight.sqlite3" \
  --expected-formal-v16-sha256 <formal-v16-sha256> \
  --backup-receipt /absolute/path/outside/project/v15-backup-receipt.json \
  --expected-backup-receipt-sha256 <backup-receipt-sha256> \
  --rollback-dir "$PWD/app/data/backups/v16-before-v15-restore-YYYYMMDD-HHMMSS" \
  --receipt /absolute/path/outside/project/v15-restore-receipt.json \
  --freeze-lock "$PWD/runtime/operator-freeze.lock"
```

恢复入口重新验证 freeze、无 DB holder、当前正式 v16 SHA、原始 v15 backup receipt、备份身份和 migration-lock 绑定；成功后将原 v16 DB/sidecar 留在新的 `--rollback-dir`。不得用 `cp`、Finder 或手写 JSON 替代。

### 回滚边界

- 正式库仍为 v15 时：可回滚代码或移回旧项目根，但 freeze lock 和已验证备份必须保留。
- v16 candidate 已安装到正式路径后：只回滚代码无效，旧代码会拒绝 v16。要么继续使用 v16 兼容代码，要么在 freeze 下用 `restore_writer_database_backup.py` 从切换前已验证的项目外 v15 备份原子恢复；禁止手工替换。
- 有界内容恢复已产生的内容、供应商费用和审计记录不回滚、不删除。数据库回滚必须按回执评估这部分差异，不得通过删审计表伪造“没有发生”。

## 历史缺口与有界内容恢复

- 不补写任何历史 `daily_capture` scheduler 槽，不写占位 `skipped/succeeded`，不伪造日调度成功。
- 已授权的内容恢复日期只有 `2026-08-17`、`2026-08-18`、`2026-08-19`。每日使用独立 `v16-gap-YYYYMMDD-range-v1` task ID、USD 4.00 task 总额硬顶、`--max-pages 8`、`--workers 1`；三日总授权 USD 12.00。`2026-08-16` 及之前和 `2026-08-20` 及之后都不自动扩日。
- 所有 phase 必须重复显式传 `--start`、`--end`、`--as-of`、`--task-id`、`--max-amount 4.00`、`--max-pages 8`、`--workers 1` 和 `--db`。非 `--full-history` 遗漏 `--start` 会被 CLI 直接拒绝；`--as-of` 必须是实际执行截面，不得将实时累计指标伪写成历史时点。
- 开始任何 phase 前先执行 `PYTHONPATH=src/dcar_eval:. .venv/bin/python -m v8.range_backfill --help`，并以当前 `--help` 为准复核参数。正式库 mutation 期间必须保持 operator freeze。
- 这是内容恢复，不是 scheduler 收据补写。它不触发过去的媒体/02:20、03:00、07:30、日报、周报或 publisher 槽的追跑。

### 单日恢复的固定执行模板

只在发布日 `RECOVERY_DATE` 对应的次日 02:00 `daily_capture` 槽缺失或终态非 `succeeded` 时执行。已是 `succeeded` 的日期必须跳过。下面的 `AS_OF` 在开始该日任务前只生成一次，所有 phase 复用同一字面值：

```bash
export PYTHONPATH="$PWD/src/dcar_eval:$PWD"
RECOVERY_DATE="2026-08-17" # 只能换成已授权的 2026-08-18 或 2026-08-19
DATE_COMPACT="${RECOVERY_DATE//-/}"
START="${RECOVERY_DATE}T00:00:00.000000+08:00"
END="${RECOVERY_DATE}T23:59:59.999999+08:00"
AS_OF="$(python3 -c 'from datetime import datetime; print(datetime.now().astimezone().isoformat(timespec="seconds"))')"
TASK_ID="v16-gap-${DATE_COMPACT}-range-v1"
DB="$PWD/app/data/dcar_insight.sqlite3"

.venv/bin/python -m v8.range_backfill --help
```

首先只读体检：

```bash
.venv/bin/python -m v8.range_backfill \
  --start "$START" --end "$END" --as-of "$AS_OF" \
  --archive-before "$START" --task-id "$TASK_ID" \
  --max-amount 4.00 --max-pages 8 --workers 1 --compact --db "$DB" \
  status
```

发现阶段同时覆盖两个平台，但不用列表页派生值关闭 detail：

```bash
.venv/bin/python -m v8.range_backfill \
  --start "$START" --end "$END" --as-of "$AS_OF" \
  --archive-before "$START" --task-id "$TASK_ID" \
  --max-amount 4.00 --max-pages 8 --workers 1 --compact --db "$DB" \
  --limit 400 --require-live-detail --skip-existing-derived-stages \
  discover

.venv/bin/python -m v8.range_backfill \
  --start "$START" --end "$END" --as-of "$AS_OF" \
  --archive-before "$START" --task-id "$TASK_ID" \
  --max-amount 4.00 --max-pages 8 --workers 1 --compact --db "$DB" \
  --history-only status
```

为兼容“日槽完全缺失”和“日槽部分写入后失败”两种情形，tag 必须先 dry-run，核对只命中该自然日后再 apply：

```bash

  --archive-before "$START" --task-id "$TASK_ID" \

```

详情只调真实 detail 接口，两平台分开限量；禁止省略 `--stage detail`，否则 CLI 默认还会执行 metrics/comments：

```bash
.venv/bin/python -m v8.range_backfill \

  --platform douyin --stage detail --history-only --limit 800 \

```

```bash
.venv/bin/python -m v8.range_backfill \
```

每个付费 phase 结束后必须在继续前核账：单日 `SUM(provider_usage.amount)` 不超过 USD 4.00；operation 只允许 `douyin_uid_profile`、`douyin_user_posts`、`xiaohongshu_user_posts`、`douyin_video_detail`、`xiaohongshu_note_detail`；不得出现 statistics/comments 付费调用。允许 discovery 同一列表响应生成 `AS_OF` 当日的零费用派生指标。任一账单、日期边界、`page_limit_reached`、detail pending 或 tag 清理门不通过都立即停止，不扩日、不换 task ID、不提高预算。

## 报告与供应商边界

- schema v16 已删除人工复核域；判定为全自动链路，不得伪造人工结论。
- 报告使用任务开始时锁定的 active release。必需数据维度不足超过合同门槛时，生成不可变 revision 并如实标记 `partial`，不得将队列数量直接写成执行 `failed`。
- TikHub 凭据保存在项目外受保护文件。Rnote 已退役，历史缓存和用量审计保留，不得恢复 Rnote 网络调用。
- 费用以 `provider_usage` 和 `provider_budget_batches` 为准。task 级总额闸门在一个 `BEGIN IMMEDIATE` 事务内跨 operation 累计；同一 task ID 第一次付费后不得改变 cap。
- 不在日志、报告、导出或 Git 中写入 API key、Cookie 或供应商 token。

## 日常备份

运行中的普通备份必须用 SQLite 在线 backup API，不能直接复制正在写 WAL 的数据库：

```bash
mkdir -p backups
sqlite3 app/data/dcar_insight.sqlite3 ".backup 'backups/dcar_insight_YYYYMMDD_HHMMSS.sqlite3'"
```

随后备份不可重建证据与报告：

- `data/cache/v8/raw_responses/`
- `data/cache/v8/media/`
- `reports/runs/v8/`
- `config/report_contract_v8_7.json`
- `config/media_processor_v8.json`

这不替代 v15→v16 切换前的项目外、已验证可恢复备份与回执。普通恢复时先保留当前数据库，恢复备份到新路径，用 `DCAR_V8_DB` 指向该路径验证；确认 health、schema identity、任务 revision 和证据 SHA 后才能切换。
