```bash
python3 - <<'EOF'
import hashlib, sqlite3, pathlib
root = pathlib.Path(".")
conn = sqlite3.connect("file:app/data/dcar_insight.sqlite3?mode=ro", uri=True)
conn.row_factory = sqlite3.Row
bad = 0
for row in conn.execute("SELECT task_id, revision, report_json_path, report_sha256 FROM report_revisions"):
    path = root / row["report_json_path"]
    actual = hashlib.sha256(path.read_bytes()).hexdigest() if path.is_file() else "<missing>"

print("mismatch:", bad)
EOF
```

要求：`mismatch: 0`。任何 BAD 都先修复登记/文件再继续。

## 3. 第二步：10+10 付费翻页试采

目的：在真实 TikHub 计费下验证 `paged-comments-v2` 的游标翻页、页级幂等、完成态判定与成本，再放量。

1. **选样**：抖音、小红书各选 10 条近 7 天内发布、声明评论数横跨低/中/高（含 1–2 条 >1000 评论以验证 `cap_reached`）的内容，记下 `content_items.id`。

2. **执行**（每条内容一次调用，带单任务花费上限）：

   ```bash
   PYTHONPATH=src/dcar_eval python3 - <<'EOF'
   from v8.providers import capture_content_comments_live
   for content_id in [/* 20 个 id */]:
       result = capture_content_comments_live(
           content_id,
           task_id=f"trial-{content_id}",
           task_max_amount=5.0,   # 单内容花费上限（币种同 provider_usage），超限即停
       )
       print(content_id, result.get("status"), result.get("completion_kind"),
             result.get("pages_fetched"), result.get("distinct_l1_comments"),
             result.get("declared_total"),
             result.get("comment_collection_coverage_percentage"))
   EOF
   ```

3. **核对**（全部满足才算通过）：

   ```sql
   -- 完成态分布：只允许 provider_exhausted / coverage_target_reached / cap_reached / zero_comments
   SELECT completion_kind, COUNT(*) FROM comment_capture_runs
   WHERE created_at >= datetime('now', '-1 day') GROUP BY 1;

   -- 页级幂等：同一 run 内无重复游标页（应为 0）
   SELECT COUNT(*) FROM (
     SELECT capture_run_id, request_cursor_sha256, COUNT(*) c
     FROM comment_capture_pages
     GROUP BY capture_run_id, request_cursor_sha256 HAVING c > 1);

   -- 身份覆盖：有稳定平台匿名键的一级评论占比（期望 ≥95%）
   SELECT ROUND(100.0 * SUM(interaction_user_id IS NOT NULL) / COUNT(*), 2)
   FROM comments c JOIN comment_evidence_versions cev ON cev.id = c.evidence_version_id
   WHERE c.parent_comment_id IS NULL;

   -- 互动用户入库
   SELECT platform, COUNT(*) FROM interaction_users GROUP BY 1;

   -- 成本
   SELECT provider, operation, SUM(billed_requests), ROUND(SUM(amount), 4)
   FROM provider_usage WHERE recorded_at >= date('now', '-1 day') GROUP BY 1, 2;
   ```

4. **中止条件**：出现游标循环告警、同一内容页数异常膨胀、成本超预算、身份覆盖率显著低于 95%、或 `declared_total_count` 与捕获数量系统性背离 —— 停止放量，把现象与 `comment_capture_runs`/`comment_capture_pages` 相关行发回给 AI 会话分析。断点续采是安全的：同窗口重跑会复用已存页（幂等槽），不重复计费已完成页。

## 4. 第三步：500 人/平台金标定标

目的：用人工金标验证 `audience-classifier-v1`，让 `active_classifier_state` 从默认 `rejected` 提升为 `approved` 或 `conservative`。**唯一登记途径是写 `config/audience_calibration_v1.json`；代码会按固定门槛重算状态，文件声明与重算不一致会整体拒绝。**

1. **抽样**（每平台 500 人；HMAC 键序 = 可复现的均匀伪随机序）：

   ```sql
   SELECT iu.id, iu.platform, iu.pseudonymous_user_key
   FROM interaction_users iu
   WHERE iu.platform = 'douyin'   -- 再跑一遍 'xiaohongshu'
     AND iu.last_seen_at >= datetime('now', '-90 day')
   ORDER BY iu.pseudonymous_user_key
   LIMIT 500;
   ```

2. **导出证据供人工标注**：对每个抽中用户导出其窗口内全部一级评论文本与所在内容标题（`gather_user_evidence` 的同口径），标注者按 `audience-definition-v1` 判 `automotive` / `not_identified`。标注规则要点：具体车型/品牌、技术问题、车主/交易行为、语境化高意向为强证据；泛化词（如"好看""不错"）永不计入；跨内容 ≥2 条实质评论也可判入。

3. **取分类器预测并计数**：

   ```bash
   PYTHONPATH=src/dcar_eval python3 - <<'EOF'
   import csv, sqlite3
   from v8.audience_classifier import evaluate_calibration
   conn = sqlite3.connect("app/data/dcar_insight.sqlite3")
   conn.row_factory = sqlite3.Row
   for platform in ("douyin", "xiaohongshu"):
       gold = {}   # user_id -> 'automotive' | 'not_identified'（从标注 CSV 读入）
       with open(f"calibration_{platform}_gold.csv", encoding="utf-8") as handle:
           for row in csv.DictReader(handle):
               gold[int(row["interaction_user_id"])] = row["gold_label"]
       predictions = {
           int(r["interaction_user_id"]): r["label"]
           for r in conn.execute(
               """SELECT interaction_user_id, label
                  FROM interaction_user_classification_versions
                  WHERE audience_definition_version='audience-definition-v1'
                    AND classifier_version='audience-classifier-v1'
                  ORDER BY interaction_user_id, id""")
       }  # 同用户多版本行时，后写入的最新行覆盖旧行
       result = evaluate_calibration(predictions, gold)
       print(platform, result.as_dict())
   EOF
   ```

4. **写定标记录**（把上一步各平台的混淆计数填入；模板见附录）并**自校验**：

   ```bash
   PYTHONPATH=src/dcar_eval python3 - <<'EOF'
   from v8.audience_rate import load_calibration_record
   value = load_calibration_record()
   print("有效状态:", value["state"])
   print("分平台:", value["platforms"])
   print("缺陷:", value["reasons"])
   EOF
   ```

   `state` 为 `approved`/`conservative` 即生效（两平台取较弱者；任一平台精度 <95% 或样本 <500 → 整体 `rejected`）。**不要为达标手工改计数**——门槛写死在代码里，改文件只会造成"声明与重算不一致 → rejected"。

5. **提交记录**：`git add config/audience_calibration_v1.json && git commit`。概览与报告下一次生成即自动采用新状态（api 与 reports 都经由 `audience_rate.active_classifier_state` 单一入口）。若定标未过：保持 rejected（页面继续显示"暂不发布"），把混淆矩阵发回 AI 会话做分类器迭代（升 `audience-classifier-v2` 后重新定标，旧记录因版本不匹配自动失效）。

## 5. 第三步之后：14 天真实刷新与观察

打开调度（`DCAR_SCHEDULER_ENABLED=1` 启动），连续观察 14 天，每天核对：

```sql
-- 采集失败率（应接近 0；retryable_failed 会被断点续采吸收）
SELECT status, COUNT(*) FROM comment_capture_runs
WHERE created_at >= datetime('now', '-1 day') GROUP BY 1;

-- 各切片去重用户量（观察 U 是否向 30 / 100 门槛爬升）
SELECT ci.platform, COUNT(DISTINCT c.interaction_user_id)
FROM comments c
JOIN comment_evidence_versions cev ON cev.id = c.evidence_version_id
JOIN content_items ci ON ci.id = cev.content_id
WHERE c.parent_comment_id IS NULL AND c.interaction_user_id IS NOT NULL
  AND ci.published_at >= datetime('now', '-7 day')
GROUP BY 1;
```

预期状态演进：`missing/below_threshold`（U 不足）→ `sample_only`（30≤U<100，或评论覆盖未达 90%）→ `available`（定标 approved + U≥100 + 身份覆盖≥95% + 评论覆盖≥90%）。这是设计行为，不要试图跳级。

`warm_up` 说明：当前概览与报告固定 `warm_up=true`（口径切换后 90 天证据窗尚未走满的提示位，仅提示、不参与状态机）。切换满 90 天后由一次小改动翻为动态判断（`default_warm_up` 已就位），届时再议，不属于本次上线范围。

## 附录 B：状态机速查（automotive_user_rate）

固定优先级，先命中先生效：无发布内容 → `not_applicable`；有内容无可识别用户 → `missing`；分类器 rejected / 身份覆盖 <95% / U<30 → `below_threshold`（不出百分比）；分类器 conservative / 30≤U<100 / 评论覆盖未知或 <90% → `sample_only`（出百分比、标样本）；全部达标 → `available`。身份覆盖故意排在人数之前：身份缺失是系统性选择偏差，堆量修不了。

## 附录 C：缺陷修复记录 — 抖音一级评论 parent_comment_id='0'（2026-08-07）

**症状**：概览页"互动用户汽车兴趣占比"各切片显示"有效样本不足"（状态 `missing`），而按附录 B 状态机，定标前的正确形态应为"覆盖不足/暂不发布"（`below_threshold`）。

**根因**：TikHub 抖音评论接口用 `reply_id="0"` 标记一级评论。旧清洗逻辑 `str(item.get("reply_id") or "") or None` 只把 `None`/空串归一为 NULL，字符串 `"0"` 被原样写入 `comments.parent_comment_id`。受众域所有一级评论过滤均为 `parent_comment_id IS NULL`（`audience_rate._slice_user_universe`、`audience_classifier.gather_user_evidence`），于是抖音用户全集 U 恒为 0，状态机在第 2 优先级命中 `missing`。全库 6,497 条抖音评论 100% 带 `'0'` 标记；小红书正确写 NULL，不受影响。

**代码修复**：
- `v8/identity.py` 新增 `normalized_parent_comment_id()`：`None/''/'0'/0 → NULL`，真实回复 id 原样通过；`insert_comment_rows` 在入库口统一归一（含历史证据回放路径）。
- `v8/providers.py`：抖音评论清洗、小红书兜底清洗、两处已清洗回放分支全部改走同一归一化函数。
- 回归测试：`tests/test_v8_comment_parent_normalization.py`。

**存量修复**（生产操作，Mark 执行）：

```bash

# 2) 干跑（只读，看 rows_to_normalize 与分平台计数）
python3 scripts/repair_comment_parent_zero.py --db app/data/dcar_insight.sqlite3
# 3) 实际执行（自动备份到 app/data/backups/，单事务 + 事后校验 + quick_check）

```
