## 0. 一句话任务

让库内 **61,800 条内容**中证据等级为 **V2/V3** 的部分完成"车型/人群/场景"三标签关联，填充 `content_spu_links / content_scene_links / content_audience_links` 三张表，使内容列表三列和「SPU人群」页统计出数。

## 1. 必读边界（防跑偏）

1. **判定逻辑已全部实现，禁止重写**。全部规则链在 `src/dcar_eval/v8/spu_audience.py`（函数索引见 §6），阈值（75/60 确认线、36 场景基础分、≥2 显式信号词等）是产品口径，**不许调整**。本方案只做：执行通道改造 + 两处规模缺陷修复 + 运行与验证。
2. 范围：只处理 `published_at IS NOT NULL` 且**最新有效评估 evidence_level ∈ {V2,V3}** 的内容。V0/V1、无评估内容直接跳过（计入 `insufficient_evidence` 计数即可，不写行、不清行）。
3. 只写四张表：三张 `content_*_links` + `spu_association_runs`。**不许触碰** evaluation/卖点/指标/评论链路的任何表。
4. 幂等：关联结果可重复重算；重算时旧行置 `invalidated_at` 不删除（`_persist_content_links` 已实现此语义）。
5. 无供应商费用：全程本地 SQLite + 本地 JSON 证据文件，不发任何网络请求。
6. 动手前先 `git add -A && git commit` 保存当前工作区，并按《运行与备份手册》备份一次数据库。近期有多个会话并发改这个仓库，开工前先确认工作区干净。

## 2. 回答"是不是只是刷新信息"——每条内容实际执行的计算

不是简单 UPDATE。每条 V2/V3 内容顺序经过五步（全部已实现）：

1. **证据文本装配**（`_content_texts`）：标题+正文来自 `content_items`；ASR/OCR 文本从 `evidence_artifacts` 取最新 available 记录的 `local_path`，读本地 JSON（`text` / `combined_text` 字段）。这是唯一的磁盘 IO 热点。
2. **车型识别三段式**（`match_series`）：①别名召回——`spu_alias` 全量词在四个文本通道做子串扫描；②语境消歧——`ambiguous=1` 的词（汉/唐/大狗/L7…）必须满足 品牌词同现 / ±5字符限定词 / ≥2个汽车语境词 之一，否则丢弃；③评分——来源分+频次分+唯一性分+语境分，按证据等级封顶（V3=100/V2=90），≥75 确认、60–74 灰区。主车型=最高分确认项。
3. **款型细化**（`resolve_trim`）：款型别名 / 年款词（20XX款）/ 价格锚（文本"X万"落入指导价带 0.9–1.1 倍）三类信号计数，唯一最优才落款型，否则记车系兜底节点（"未细化"）。
4. **场景直判**（`match_scenes`）：S1–S11 触发词扫描，36 基础分+来源分+频次分 ≥60 确认；有负向词时要求 ≥2 个不同触发词。多值。
5. **人群归因+一致性**（`attribute_audience`）：内容显式信号（≥2 个不同词）优先，否则走主车型→`spu_audience_map` 的规则先验；两者冲突置 `conflict_flag`；实测场景超出该人群 core∪related 场景集置 `consistency_flag`（供 gap 分析，不改判）。

单条成本 ≈ 3–5 次 SQL + ≤2 次小 JSON 文件读 + 约 250 词×4 通道的子串扫描。61,800 条全量估计 **10–30 分钟**（视 V2/V3 占比与磁盘），这就是必须改执行通道的原因。

## 3. 现状缺陷（Codex 必修，按序号交付）

### T1（缺陷修复，P0）：`content_labels` / `build_stats` 在 6 万条规模会触发 SQLite 变量数上限

`content_labels()`（spu_audience.py:901 起）用 `IN (?,?,...)` 展开 content_ids；`build_stats()`（:1198 起）把窗口内**全部**内容 id 传进去。窗口=全部时是 61,800 个占位符，超过 SQLite 默认上限（SQLITE_MAX_VARIABLE_NUMBER，多数构建为 32,766，旧构建 999），会抛 `too many SQL variables`。内容列表页只传 ≤100 个 id 不受影响；**统计页在关联出数后必崩**。

修法（二选一，倾向 a）：
- a. `content_labels` 内部按 ≤900 个 id 分块循环查询后合并（三处查询同改）；
- b. `build_stats` 不再传 id 列表，改为把窗口/平台谓词直接下推到三张 links 表的 JOIN `content_items` 查询里（`content_labels` 保留给内容列表用）。

验收：`build_stats(window="all")` 在 61,800 条内容、任意关联行数下不抛异常；现有容器冒烟逻辑不回归。

### T2（缺陷修复，P0）：`run_association` 逐条点查证据等级 + 全量内容遍历

现状（spu_audience.py:775 起）：遍历**所有** published 内容，每条单独执行 `_latest_evidence_level`（一次窗口点查），61,800 次；V0/V1 内容也会走一次"清行"事务。

修法：
- 用一条窗口查询批量取全部内容的最新有效评估等级（模式参考 `evaluation_selectors.py` 的 `ROW_NUMBER() OVER (PARTITION BY content_id ORDER BY evaluated_at DESC, id DESC)`，条件 `invalidated_at IS NULL`），在 Python 侧建 `{content_id: level}` 字典；
- 主循环只进 V2/V3 内容；非 V2/V3 **直接跳过**（只累计 `insufficient_evidence`，不再为其开事务清行——首跑它们本来就没有行；如担心历史残留，可在 run 开始时用一条 SQL 统计非 V2/V3 内容当前有效行数，>0 才做一次性批量失效）；
- ASR/OCR 的 `local_path` 同样可以两条窗口查询批量预取（按 artifact_type 组、每 content 取 id 最大且 available 且 sha256 非空的一条），替代逐条 `_latest_artifact_path`；
- 落库事务从"每条一个事务"改为**每 500 条一批**提交（保持每批内先失效后插入的顺序）；
- 每处理 1,000 条向日志/进度行写一次进度。

验收：`--limit 2000` 试跑相对现版本提速明显（点查消失）；结果行与现版本在同一样本上逐行一致（可用 limit 500 双跑对比三张表的 (content_id, spu_id/scene_code/audience_code, score, status) 集合）。

### T3（执行通道，P0）：给回刷一个不经 HTTP 的入口 + API 后台化

现状 `POST /api/v8/spu-audience/associate` 是同步接口，6 万条会让请求挂 10–30 分钟，浏览器/网关都可能中断。

- a. **新增 CLI 脚本 `scripts/run_spu_association.py`**（首跑用它）：参数 `--limit N`、`--dry-run`（只统计 V2/V3 条数、别名表规模、预计处理量，不写库）、`--batch-size`（默认 500）；打印进度与最终 summary（沿用 `spu_association_runs` 计数字段）。注意调度器与 API 不用停：SQLite 写锁由现有 `connect()` 的 busy 配置兜底，但**建议在每日采集/调度空窗期跑**，避免长写锁竞争（参考 README：调度默认关闭）。
- b. **API 改后台**：`associate` 端点改为创建 `spu_association_runs` 行后用 FastAPI `BackgroundTasks` 执行（模式抄 api.py 里报告任务的 `background.add_task(_run_task_in_background, ...)`），立即返回 `{run_id, status:"running"}`；页面已有 `last_run` 展示，只需把「运行关联」按钮改为提交后轮询 `GET /api/v8/spu-audience/assets`（每 5 秒）直到 `last_run.status` 终态，运行中按钮置灰显示"关联运行中…"。`spu_association_runs` 建议加一列 `processed_count`（或复用 `summary_json` 写进度），供轮询显示"已处理 x / y"。
- c. 防并发：同一时刻只允许一个 running 的关联 run（发起时检查有 running 行则 409 返回中文提示"已有关联任务在运行"）。进程崩溃留下的孤儿 running 行，服务启动时置 failed（参考 `_recover_interrupted_tasks` 的做法）。

验收：CLI 全量跑通出 summary；页面点按钮立即返回、进度可见、完成后统计与三列出数；重复点击被 409 拦截。

### T4（运行 runbook，P1）：实际执行顺序

1. `git commit` + 数据库备份；
2. `python -m` 或 `scripts/run_spu_association.py --dry-run`：确认 V2/V3 内容量、别名词数（约 44 车系 ~120 词）、预计耗时；
3. `--limit 500` 试跑：跑完执行 §5 验证 SQL 抽查，人工看 20 条（重点：歧义词"汉/唐/大狗/L7"没有误命中、对比类内容主车型合理）；
4. 全量跑（记录耗时）；
5. §5 全量验证 + 页面验证（内容列表三列、SPU人群页统计/单维榜/gap、筛选器）；
6. 把 run summary（总数/归到车型/细化/灰区/场景/人群/证据不足）回贴给 Mark。

### T5（可选，P2）：`--only-missing` 增量模式

给 CLI 加开关：只处理"当前没有任何有效关联行"的 V2/V3 内容，供后续日常增量用（新内容评估完成后补关联）。全量语义保持默认。

## 4. 预期结果与不确定性（提前对齐，避免误判为 bug）

- **车型覆盖率不会高**：种子只有 44 个车系+保守别名。大量内容（泛知识、剧情、无车系指向）本来就不该命中；另一部分是词表没覆盖。跑完后把"含 ≥2 个汽车语境词但未命中任何车系"的高频标题词导出 Top 100（可作为 T4 附加产出），交 Mark 决定扩哪些车系——这是方案设计里的词表迭代抓手，不是缺陷。
- **人群列大部分会是"规则推断"**：显式信号要 ≥2 个词才直判，属预期。
- **场景多值**：跨场景条数求和 > 内容总数是口径（命中即计），页面脚注已声明。
- 曝光列在"已归类曝光覆盖 <90%"时显示"暂不发布"，同样是口径不是 bug。

## 5. 验证 SQL（跑完必查）

```sql
-- 总量对账
SELECT status, COUNT(*) FROM spu_association_runs GROUP BY status;
SELECT COUNT(*) FROM content_spu_links WHERE invalidated_at IS NULL AND is_primary=1;          -- = summary.spu_linked
SELECT COUNT(*) FROM content_spu_links WHERE invalidated_at IS NULL AND status='gray';
SELECT COUNT(DISTINCT content_id) FROM content_scene_links WHERE invalidated_at IS NULL;       -- = summary.scene_linked
SELECT COUNT(*) FROM content_audience_links WHERE invalidated_at IS NULL;                      -- = summary.audience_linked

-- 分布合理性（人工过目）
SELECT c.series, COUNT(*) n FROM content_spu_links l JOIN spu_catalog c ON c.spu_id=l.spu_id
WHERE l.invalidated_at IS NULL AND l.is_primary=1 GROUP BY c.series ORDER BY n DESC LIMIT 20;
SELECT scene_code, COUNT(*) FROM content_scene_links WHERE invalidated_at IS NULL GROUP BY scene_code ORDER BY 2 DESC;
SELECT audience_code, source, COUNT(*) FROM content_audience_links WHERE invalidated_at IS NULL GROUP BY 1,2;

-- 歧义词误命中抽查（应为 0 或极少：确认"汉"没把人名/汉兰达吸进来等）
SELECT l.content_id, ci.title, l.evidence_json FROM content_spu_links l
JOIN content_items ci ON ci.id=l.content_id JOIN spu_catalog c ON c.spu_id=l.spu_id
WHERE l.invalidated_at IS NULL AND c.series='汉' ORDER BY RANDOM() LIMIT 10;

-- 一致性/冲突规模（gap 看板数据源）
SELECT SUM(conflict_flag), SUM(consistency_flag) FROM content_audience_links WHERE invalidated_at IS NULL;
```
